# 从车端采集到控制执行：自动驾驶地图的数据生命周期

<p class="post-meta">2026-08-05 · GIS 全链路 · 自动驾驶地图 · 约 20 分钟</p>

一辆无人车驶过园区边缘，发现原来封闭的位置似乎多出了一条新通道。

相机看到了道路边界，激光雷达扫到了可以通行的地面，GNSS 和 IMU 记录了车辆经过这片区域的轨迹。车辆能不能立刻把这条通道写进正式地图，再告诉其他车辆从这里走？

答案通常是否定的。

单车看到的可能是真实道路，也可能只是一次临时绕行、施工便道、定位漂移或感知识别错误。即使几何位置正确，它也未必知道这条路允许什么车辆进入、是否单向通行、连接到哪条主路，以及什么时候可以正式启用。

因此，自动驾驶地图并不是一份制作完成后放进车辆的静态文件。它是一条持续运行的数据链：

```text
车端观察现实
→ 生成局部地图和候选变化
→ 云端融合、编辑、质检并形成正式版本
→ 编译成车辆可以高效读取的地图包
→ 车端加载地图，完成定位、规划和控制
→ 运行中继续发现变化
→ 进入下一轮更新
```

这篇文章不再从某一种地图格式出发，而是跟随同一批道路信息，看它怎样在车端和云端之间流动、改变形态、提高可信度，并最终转化为车辆的运动。

## 先看完整闭环

整条生命周期可以分成三个责任域。

```text
┌──────────────────────────────────────────────┐
│ 车端采集域                                   │
│ 相机 / LiDAR / GNSS / IMU                   │
│        ↓                                     │
│ 感知、定位、局部建图                         │
│        ↓                                     │
│ Candidate Map Patch                         │
└──────────────────┬───────────────────────────┘
                   │ 上传候选变化与证据
                   ↓
┌──────────────────────────────────────────────┐
│ 云端生产域                                   │
│ 接入 → 多车融合 → 地图编辑 → 拓扑构建       │
│      → 规则质检 → 版本冻结 → 地图编译       │
│      → 发布                                  │
└──────────────────┬───────────────────────────┘
                   │ 全量包 / 增量包 / 动态事件
                   ↓
┌──────────────────────────────────────────────┐
│ 车端运行域                                   │
│ 下载 → 校验 → 加载 → 定位与地图匹配         │
│      → 全局路线 → 局部规划 → 车辆控制       │
└──────────────────┬───────────────────────────┘
                   │ 运行反馈
                   └──────────────→ 下一轮更新
```

这里所说的“云端”，不一定是远端公网云。在矿区、港口、工厂和物流园区，它也可能是部署在现场机房的场端服务器或边缘数据中心。关键区别不在机器放在哪里，而在责任：它是否拥有多车和全局视角，是否负责生产并发布正式地图。

## 数据并不是以同一种形态走完整条链路

理解生命周期最重要的一步，是不要把每个阶段的产物都叫作“地图”。

| 阶段 | 主要数据形态 | 可信程度 | 主要用途 |
| --- | --- | --- | --- |
| 传感器采集 | 图像、点云、GNSS/IMU 轨迹 | 原始观测 | 描述车辆看到和测到的世界 |
| 局部建图 | 边界、中心线、可行驶区域、局部语义 | 本车短时可信 | 实时规划或生成变化候选 |
| 候选 Patch | 局部变更提案、证据、来源和置信度 | 待确认 | 上传云端融合与审核 |
| 生产地图 | 可编辑的几何、拓扑、语义和规则 | 质检前不可发布 | 地图生产、协作和审核 |
| 正式地图版本 | 审核通过的不可变快照 | 权威数据 | 作为编译和发布输入 |
| 车端地图包 | 二进制地图、空间索引、邻接表和清单 | 可运行制品 | 快速加载、查询和路径搜索 |
| 运行时世界模型 | 基础地图、动态事件与实时感知的叠加 | 随时间变化 | 局部规划和安全决策 |
| 规划控制结果 | 路线、轨迹、转角、加速度和制动请求 | 当前执行结果 | 驱动车辆运动 |

同一条新通道，最初只是点云和轨迹中的一组观测，随后成为候选变化，再成为正式版本中的道路对象，最后被编译为车端路网节点和索引记录。数据的形态、负责人和使用条件一直在变化。

## 第一阶段：车端先负责看见世界

车端采集通常来自多种传感器。

### 相机提供语义

相机容易识别车道线、道路边缘、标志牌、箭头、停止线和可行驶区域。它擅长回答“这是什么”，但图像中的像素还需要结合相机标定、车辆姿态和其他传感器，才能落到稳定的空间坐标中。

### 激光雷达提供几何

LiDAR 记录周围环境的三维点，可以帮助估计地面、坡度、路缘、墙体、障碍物和道路边界。点云几何直接，却会受到遮挡、扬尘、雨雪、反射强度和车辆运动的影响。

### GNSS 和 IMU 提供位姿线索

GNSS 提供全局位置，IMU 描述姿态和运动变化。二者与轮速、视觉或 LiDAR 定位融合后，形成车辆在某个时间点的位姿：

```text
VehiclePose
├─ position: x, y, z
├─ orientation: roll, pitch, yaw
├─ velocity
├─ timestamp
└─ uncertainty
```

时间戳和不确定性与坐标同样重要。没有时间同步，多帧点云会被错误地拼在一起；没有误差描述，云端就难以判断两辆车上报的道路偏移究竟是现场变化还是定位噪声。

这一阶段的责任可以概括为：

> 车端感知负责看见对象，定位负责把观测放到空间中，但它们还没有生产出可以全局发布的正式地图。

## 第二阶段：局部建图把观测变成地图原材料

单帧传感器只能看到某个瞬间。局部建图需要把一段时间内的观测放进同一个局部坐标或全局坐标中：

```text
传感器标定与时间同步
→ 位姿估计
→ 多帧配准
→ 道路与可行驶区域识别
→ 几何融合和平滑
→ 局部地图
```

局部地图可能包含：

- 当前道路边界和中心趋势；
- 可行驶区域；
- 路口或分叉结构；
- 障碍物与占用空间；
- 停止线、路缘和道路标志；
- 每个结果的置信度和有效时间。

它首先服务本车。即使云端没有任何响应，车辆也必须依靠实时感知处理前方障碍、道路边缘变化和临时施工。

但局部地图通常只有几十米到几百米范围，而且可能存在断裂、重复、漏检、几何抖动和错误连接。它能回答“眼前现在是什么样”，却不一定知道：

- 这条路在整个园区中通向哪里；
- 它是否属于当前正式运营路网；
- 哪种车辆可以进入；
- 是否需要让行或限制速度；
- 与远处道路怎样形成完整拓扑；
- 这一变化是临时现象还是长期事实。

所以局部建图的成果既可以直接进入本车局部规划，也可以成为地图更新的原材料，但不能自动等同于正式地图。

## 第三阶段：候选地图 Patch 是一份变更提案

当车端发现局部地图与基础地图长期不一致时，可以生成 `Candidate Map Patch`。

Patch 的含义是“补丁”：它只描述局部变化，而不是再次上传整个地图。Candidate 则表示它仍然待确认。

一份候选 Patch 可以写成：

```json
{
  "patchId": "patch_20260805_001",
  "baseMapVersion": "V102",
  "sourceVehicle": "vehicle_12",
  "changeType": "add_road",
  "observedAt": "2026-08-05T14:30:00+08:00",
  "observationCount": 8,
  "confidence": 0.87,
  "geometry": {
    "type": "LineString",
    "coordinates": []
  },
  "topologySuggestion": {
    "predecessorIds": ["road_A"],
    "successorIds": ["road_C"]
  },
  "evidenceRefs": ["trajectory_128", "pointcloud_451"],
  "status": "pending"
}
```

它至少要回答：

- 哪里发生了什么变化；
- 建议新增、删除还是修改哪个对象；
- 基于哪一个正式地图版本判断出差异；
- 由哪辆车在什么时间观察到；
- 观察了多少次，置信度多高；
- 候选几何和拓扑是什么；
- 有哪些轨迹、点云或图像证据可以复核。

Patch 比上传整张地图更适合更新闭环，因为它数据量小、修改范围清晰、容易审核、便于多车融合，也能追踪某一项变化最终被接受还是拒绝。

::: warning 候选 Patch 不是正式 Map Patch
`Candidate Map Patch` 可能来自误检，不能直接写入车辆共同使用的权威地图。只有经过融合、编辑、质检和审核的变更，才可以成为 `Approved ChangeSet`，进入新的正式地图版本。
:::

## 第四阶段：上传之前和接入之后都要检查上下文

上传不只是把一个 JSON 发给服务器。系统还要同时处理：

- 车辆身份和数据来源；
- 坐标参考、局部原点与转换参数；
- 传感器和算法版本；
- 当前使用的基础地图版本；
- 数据采集时间和有效范围；
- 文件完整性与重复上传；
- 弱网下的断点续传和任务重试。

`baseMapVersion` 尤其关键。假设车辆仍在使用 V100，而云端已经发布 V102，它识别出的“新增道路”可能早已存在于新版本中。如果不先比较版本，平台就会把旧车的迟到数据当作新变化。

云端接入后通常先完成格式校验、坐标转换、范围检查、版本比对和去重，再把候选 Patch 放入待融合任务，而不是直接打开地图编辑器让人处理。

## 第五阶段：云端融合把单车观察变成多源证据

单辆车的一次观测不够稳定。云端拥有多车和更长时间范围的数据，可以把相同区域的候选结果聚合起来：

```text
Vehicle A：疑似出现新通道
Vehicle B：轨迹支持该通道存在
Vehicle C：识别到相同道路边界
        ↓
坐标统一与版本对齐
        ↓
重复候选聚类
        ↓
几何拟合与置信度更新
        ↓
云端候选道路 candidate_road_01
```

融合阶段主要处理四类问题。

### 几何是否一致

不同车辆上报的中心线不会完全重合。系统需要根据定位精度、观测次数和数据质量进行配准、拟合和平滑，而不是简单求平均。

### 变化是否持续存在

一辆车绕开临时障碍形成的轨迹，不应该马上被识别成新路。相同变化是否被多车、多次、跨时间段观察到，是判断长期变化的重要依据。

### 候选之间是否冲突

两份 Patch 可能分别建议新增道路和扩大禁行区，或者基于不同地图版本修改同一对象。平台需要检测空间重叠、对象冲突和版本冲突。

### 证据是否足以进入生产

低置信度结果可以继续等待观测，高置信度结果可以自动创建编辑任务，安全影响大的变化则必须要求人工复核或仿真验证。

融合并不代表正式确认。它只是把大量零散观测整理成一份更可信、更容易审查的候选结果。

## 第六阶段：地图生产把候选结果变成规范对象

候选道路进入生产平台后，地图人员和自动化工具开始补全它缺失的几何、拓扑、语义和规则。

### 几何编辑

需要修正中心线、左右边界、道路宽度、高程、坡度、曲率和连接处的平滑关系。生产人员关注的不只是画面是否顺眼，还要判断大型车辆的转弯包络和制动距离是否允许实际通行。

### 拓扑构建

一条道路在 GIS 中与另一条线接触，不代表车辆能够从一条路驶入另一条路。地图必须显式表达：

```text
predecessor / successor
left / right neighbor
允许或禁止的转向
路口内部连接
道路方向
```

拓扑决定路径搜索能否穿过路口，也决定车辆是否会被引导到错误方向。

### 业务语义补全

传感器可以看见道路，却看不见企业运营规则。地图平台还要维护：

- 限速和通行方向；
- 允许的车型、载重、宽度和高度；
- 装载区、卸载区、停车区和充电区；
- 禁行区、会车区和等待点；
- 班次、天气或作业状态下的通行条件；
- 生效时间和失效时间。

因此比较清晰的专业边界是：

> 感知团队负责“看见并识别”，建图算法负责“融合成候选地图”，地图生产团队负责“做成符合标准的正式地图”。

## 第七阶段：质检和审核决定它能不能成为正式事实

地图编辑完成后不能直接发布。质量检查至少包括四层。

| 检查层级 | 典型问题 |
| --- | --- |
| 几何 | 自相交、折返、异常短线、边界交叉、曲率突变 |
| 拓扑 | 前驱后继不对称、孤立道路、错误转向、路网不连通 |
| 属性 | 缺少限速、方向、车型限制、生效时间或对象类型 |
| 业务 | 坡度超限、道路过窄、装卸点不可达、禁行规则冲突 |

系统可以自动阻止致命错误发布，但自动规则无法确认所有现场语义。高风险修改还可能经过：

```text
人工审核
→ 历史轨迹回放
→ 仿真路线验证
→ 小范围试运行
→ 正式批准
```

通过审核的变更才从 `Candidate Map Patch` 变成 `Approved ChangeSet`。这一状态变化看起来只是一行字段，实际上代表数据责任发生了根本变化：它不再是车辆的观察，而是平台准备承担发布责任的正式变更。

## 第八阶段：版本管理保存每一次正式变化

地图不应该通过反复覆盖同一个文件来更新。正确的过程更接近：

```text
Map V102
  + Approved ChangeSet 2026-08-005
        ↓
生成不可变发布快照
        ↓
Map V103
```

一个版本需要记录：

- 它从哪个基础版本产生；
- 新增、修改和删除了哪些对象；
- 每项变化来自哪些候选 Patch；
- 谁编辑、谁审核、为什么修改；
- 通过了哪一套质检规则；
- 面向什么区域、车型和软件版本；
- 何时生效，以及失败时回退到哪一版。

这里最好区分四个概念：

```text
Candidate Map Patch
→ 待确认的局部变化提案

Approved ChangeSet
→ 已审核通过的一组正式修改

Map Version
→ 应用修改后形成的不可变地图快照

Map Package
→ 由某个版本编译出的车端运行制品
```

有了这条追溯链，车辆出现异常时才能从 `Map Package` 找到源版本，再找到具体 ChangeSet 和最初的观测证据。

## 第九阶段：地图编译把生产数据变成车辆制品

生产地图适合编辑和审核，通常保留丰富属性、历史记录和数据库关系。车辆则关心启动速度、内存占用、局部查询延迟和断网可用性。它不应该在每次规划时远程查询生产数据库。

因此发布之前还需要地图编译：

```text
正式地图快照
→ 固化对象 ID
→ 检查引用完整性
→ 建立道路邻接表
→ 建立空间网格或树索引
→ 几何简化、量化或压缩
→ 按区域分块
→ 二进制序列化
→ 生成清单、校验值和签名
```

一种简化制品可能是：

```text
map.bin        # 几何、属性和拓扑
map.index      # 空间索引与分块目录
manifest.json  # 版本、范围、兼容性和校验值
```

编辑格式强调可维护性，车端格式强调确定性和效率。地图编译器就是连接这两个目标的边界。

同一个 `Map Version` 还可能编译出多种制品：定位使用点云或特征地图，规划使用矢量路网，调度系统使用较粗粒度的道路与作业区模型。它们内容不同，但必须能追溯到同一正式版本，避免各模块对现实世界持有互相矛盾的理解。

## 第十阶段：发布不只是提供一个下载地址

发布系统要回答谁可以获得哪个版本，以及怎样安全切换。

```text
地图包入库
→ 指定区域、车辆组和生效时间
→ 灰度发布或全量发布
→ 车辆下载
→ 完整性与兼容性校验
→ 本地预加载
→ 在安全时机原子切换
→ 上报安装结果
```

为了节省带宽，系统可以同时支持全量包和增量包。但增量更新必须明确基础版本。例如 `V102 → V103` 的差分不能直接应用到仍在使用 V100 的车辆上。

车辆下载完成也不代表更新成功。它还要检查文件校验值、地图范围、格式版本、车辆软件兼容性和对象引用。切换过程中应保留旧版本；如果加载或自检失败，车辆能够继续使用上一版，而不是停留在一套安装到一半的地图上。

地图发布最终追求的是车队一致性：平台不仅知道“V103 已发布”，还应知道哪些车辆已经下载、哪些已经激活、哪些仍在旧版本，以及云端任务和路线是否与车辆当前版本兼容。

## 第十一阶段：车端加载地图并建立运行时能力

地图进入车辆后，由车端地图引擎负责加载和查询。常见能力包括：

```text
loadMap()
queryAround()
locateRoadOrLane()
getPredecessors()
getSuccessors()
getSpeedLimit()
validateRoute()
findRoute()
```

加载不是把整个文件反序列化到一个巨大对象中。车端通常会根据当前位置加载附近分块，建立或读取空间索引，缓存当前路线周围的几何和拓扑，并在车辆移动时更新局部窗口。

此时，正式基础地图只是运行时世界模型的一层：

```text
稳定基础地图
      +
动态道路状态
      +
实时局部感知
      ↓
车辆当前使用的局部世界模型
```

地图负责提供较稳定的全局骨架、拓扑、作业语义和长期规则；动态状态描述临时封路和运营变化；实时感知处理障碍物、人员、车辆、落石和道路边缘的即时变化。

## 第十二阶段：从定位开始，把地图转化为车辆运动

车辆拥有地图后，仍需要把实时状态放进地图的坐标和拓扑中。

### 定位与地图匹配

GNSS、IMU、轮速、视觉或 LiDAR 定位先产生车辆位姿。地图匹配再判断车辆位于哪条道路或车道，并计算沿道路位置、横向偏移和航向关系。

```text
VehiclePose + LocalMap
→ Road ID / Lane ID
→ s / lateral offset / heading error
```

这里不能只找几何上最近的道路，还要考虑方向、边界、历史轨迹和拓扑连续性。但地图匹配只是整个生命周期进入车端运行后的一个环节，并不是地图生命周期本身。

### 全局路线

全局路线回答“从当前位置经过哪些道路到达目标”。它本质上是在带有方向、代价和车辆约束的路网图上搜索。

全局路线并不天然只属于云端或车端：

- 任务分配、多车调度和全局路权通常偏云端或场端；
- 云端可以结合全局交通状态生成推荐路线；
- 车端可以校验路线，并在断网、偏航或临时封路时本地重规划。

比较稳健的架构是：

```text
云端下发任务、目标或推荐路线
        ↓
车端结合本地地图进行校验
        ↓
必要时车端重新搜索可行路线
```

所以更准确的说法是：

> 全局决策偏云端，路径搜索可云可端，安全执行一定在端。

### 局部规划

局部规划处理车辆未来几秒或几十米内的运动：跟车、绕障、转弯、会车、停车和避让。它必须结合最新感知结果，并在车端实时执行。

```text
全局路线
 + 当前地图和道路规则
 + 障碍物与可行驶区域
 + 车辆动力学状态
        ↓
局部可执行轨迹
```

### 控制车辆

控制模块跟踪局部轨迹，产生转向、驱动和制动请求。到这里，一条最初存在于点云和轨迹中的候选道路，才真正通过地图数据链影响车辆运动。

地图没有直接控制方向盘。它通过定位结果、路网路线、道路约束和局部轨迹，逐层转化为控制输入。

## 两种变化必须走两条更新通道

并不是现实世界中的每次变化都应该触发地图生产和版本发布。

### 稳定结构变化进入地图版本

例如：

- 新增或废弃道路；
- 道路边界长期改变；
- 拓扑连接改变；
- 装载点、仓库或站点迁移；
- 长期通行方向和业务规则变化。

它们适合进入：

```text
Candidate Map Patch
→ 融合、编辑和质检
→ Approved ChangeSet
→ Map V103
→ 编译并发布
```

### 高频临时变化进入动态事件

例如：

- 事故或临时施工；
- 一小时封路；
- 临时限速；
- 某个作业区短时禁行；
- 道路积水或设备占道。

它们更适合成为带有效期的 `Dynamic Road Event`：

```json
{
  "eventType": "ROAD_CLOSED",
  "roadId": "road_008",
  "effectiveAt": "2026-08-05T15:00:00+08:00",
  "ttl": 3600,
  "reason": "temporary_construction"
}
```

```text
动态事件发布
→ 车端叠加到当前基础地图
→ 将道路标记为暂不可通行
→ 立即重新规划
→ 到期或撤销后恢复
```

如果每次十分钟封路都重新生产整套地图，系统会被版本、编译和分发延迟拖住；如果长期新增道路永远只作为临时事件，又会失去完整拓扑、质量审核和版本追溯。

因此可以记住：

> 临时状态走动态事件，稳定事实进入地图版本。

## 车端不是被动消费者，而是闭环的起点和终点

车辆执行路线后，会继续比较地图、定位与现实感知：

```text
地图说前方可通行
但多辆车持续绕行

地图说这里没有道路
但多辆车稳定通过同一通道

地图边界位于左侧
但感知长期检测到明显偏移
```

这些差异可以触发变化检测，生成新的候选 Patch。不过车端仍不能直接改写所有车辆共同使用的正式地图，因为单车观测可能受到定位漂移、传感器遮挡、临时障碍或算法版本问题影响。

完整反馈应该保留：

- 发现变化的车辆和时间；
- 当前使用的地图与软件版本；
- 原地图对象和候选结果；
- 原始或摘要证据；
- 重复观测次数和空间误差；
- 对定位、路线和安全的影响。

然后它再次进入云端融合、编辑、质检、版本和发布流程。地图生命周期由此闭合。

## 走完一个具体案例：车辆发现一条新通道

现在把所有阶段放回开头的故事。

### 1. 车端观察

车辆 12 多次经过园区边缘。相机识别到道路边缘，LiDAR 发现连续可行驶地面，GNSS/IMU 轨迹显示车辆稳定通过。

### 2. 局部建图

车端把多帧观测融合成一段候选中心线和可行驶区域。它可以在本次任务中把这片区域作为实时局部环境处理，但暂不修改正式路网。

### 3. 生成候选 Patch

系统发现局部道路与 Map V102 不一致，于是生成 `add_road` 候选，附带基础版本、置信度、轨迹和点云证据后上传。

### 4. 云端融合

车辆 8 和车辆 19 后续也上报相同区域。平台完成坐标统一、候选聚类和几何拟合，把三辆车的结果合并为 `candidate_road_01`。

### 5. 编辑和拓扑构建

地图生产人员修正道路边界，确认它连接 `road_A` 与 `road_C`，补充通行方向、限速、允许车型和生效时间。

### 6. 质检与审核

规则检查发现新道路出口的转弯半径不满足大型车辆要求。生产人员调整连接几何，再次检查通过，并完成现场确认。

### 7. 生成正式版本

候选变更成为 Approved ChangeSet，平台基于 V102 生成不可变的 Map V103。

### 8. 编译和发布

编译器建立新的道路邻接表、空间索引和地图分块，生成 V103 的全量包及 V102 到 V103 的增量包。

### 9. 车端切换

目标车辆下载、校验并预加载新版本，在停车或任务边界完成原子切换，并向平台上报激活结果。

### 10. 规划与控制

云端调度给出新的运输目标，车端全局路线搜索选择新通道。局部规划结合实时障碍物生成轨迹，控制模块最终驱动车辆通过。

### 11. 再次反馈

如果多辆车持续在新道路入口偏离中心线，系统重新生成几何偏移候选，开始下一轮地图修订。

这才是一条道路从被看见到被车辆正式使用的完整生命周期。

## 云端和车端的职责最终怎样划分

| 能力 | 云端或场端 | 车端 |
| --- | --- | --- |
| 原始传感器采集 | 接收和归档 | 主要负责 |
| 实时感知与局部建图 | 可离线重算和融合 | 主要负责 |
| 候选地图生成 | 可由云端算法生成 | 可检测并上报 |
| 多车融合 | 主要负责 | 不负责全局融合 |
| 地图编辑与语义补全 | 主要负责 | 消费结果 |
| 拓扑构建和规则质检 | 主要负责 | 加载并校验必要规则 |
| 正式版本与编译发布 | 主要负责 | 不修改权威版本 |
| 地图下载、加载和局部查询 | 提供制品 | 主要负责 |
| 定位和地图匹配 | 可用于离线分析 | 实时负责 |
| 任务与多车调度 | 主要负责 | 接收并校验 |
| 全局路线 | 可计算推荐路线 | 可搜索、校验和重规划 |
| 局部规划和避障 | 不进入实时安全闭环 | 必须负责 |
| 车辆控制与安全停车 | 不直接控制 | 必须负责 |

没有一条绝对边界能适用于所有公司，但三个原则比较稳定：

1. 需要多车和全局视角的生产、版本与调度偏云端；
2. 需要毫秒级响应、断网可用和安全兜底的能力放车端；
3. 云端维护正式地图，车端持续提供现实变化的证据。

## 最后总结

自动驾驶地图的数据生命周期，不是“采集一张地图，然后发给车辆”，而是现实世界、云端生产系统和车端运行系统之间的持续协作：

```text
车辆看见变化
→ 局部建图形成地图原材料
→ Candidate Map Patch 描述待确认变化
→ 云端多车融合提高可信度
→ 编辑、拓扑和规则补全可计算语义
→ 质检与审核建立发布责任
→ 版本管理冻结可追溯事实
→ 地图编译生成高效车辆制品
→ 发布系统保证安全切换和车队一致性
→ 定位、路线、局部规划和控制消费地图
→ 车辆运行继续发现新的变化
```

这条链路中，最重要的并不是某一种高精地图格式，而是数据责任的逐步转换：

> 原始观测不能直接成为正式事实，正式事实也不能直接成为车辆动作。它必须经过候选、融合、生产、验证、版本、编译和运行时融合，最终才转化为可执行轨迹。

当地图能够从车辆回到云端，又从云端安全地回到车辆，它才真正拥有完整的生命周期。
