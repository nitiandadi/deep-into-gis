# 自动驾驶中的 GIS：从高精地图、轻地图到在线语义地图

<p class="post-meta">2026-07-23 · GIS 全链路 · 自动驾驶 · 约 20 分钟</p>

如果关闭车机地图和 RViz，可不可以让自动驾驶系统继续运行？

答案是：可以。只要定位、感知、规划和控制所需的数据仍然存在，车辆并不需要先把高精地图画到屏幕上，再从像素中理解道路。

它直接消费的是另一种地图：

```text
点云地图提供稳定环境几何
矢量地图提供车道、边界、停止线和交通规则
局部占据地图提供当前障碍与可通行空间
在线语义地图提供传感器刚刚识别出的道路结构
```

这些数据经过坐标转换、局部加载、空间查询和拓扑推理，直接进入算法：

```text
地图与传感器数据
→ 定位：车辆在哪里
→ 感知：周围有什么、位于什么道路结构中
→ 规划：接下来可以怎样行驶
→ 控制：怎样转向、加速和制动
```

渲染只是旁边的一条支路，用于调试、仿真、监控和人机交互。

这使自动驾驶成为非常典型的“GIS 不以地图画面为终点”的系统。但如果只用传统高精地图解释它，又会落后于今天的工程现实：轻地图、在线局部地图、占据表示和隐式地图正在改变车辆使用空间先验的方式。

理解这些概念的第一步，是不要把它们混成同一条分类。

## 先拆开三个经常混淆的维度

“高精地图、轻地图、语义地图、在线地图、占据地图、隐式地图”并不处于同一个维度。

可以先问三个问题：

1. 地图表达什么？
2. 地图什么时候、在哪里产生？
3. 算法对预制地图依赖多强？

### 维度一：地图表达什么

```text
几何表达：点云、表面、道路边界和三维结构
语义表达：车道、停止线、交通灯、限速和通行规则
拓扑表达：车道前后、左右、合流、分流与路口连接
占据表达：空间是空闲、占用还是未知
特征表达：适合定位的关键点、地标或神经特征
```

### 维度二：地图怎样产生

```text
离线专业生产：测绘车采集、加工、质检后发布
众包更新：多车采集变化，云端融合后下发
车端在线构建：根据当前相机或 LiDAR 实时生成局部地图
时序维护：把过去帧和当前帧融合成持续更新的局部表示
```

### 维度三：车辆依赖多少预先地图

```text
强地图依赖：定位和规划建立在高精先验地图上
轻地图依赖：只保留关键骨架，其余由感知补充
弱地图依赖：使用导航路线或粗粒度道路信息
无传统高精地图：在线构建或在神经网络内部形成空间表示
```

因此，“语义地图”不一定比“轻地图”更重；轻地图也可以是一张精简语义地图；在线地图同样可以输出高精矢量语义。

不能简单写成：

```text
高精地图 → 轻地图 → 语义地图
```

更准确的关系是一个组合空间：

| 示例 | 表达内容 | 生产方式 | 地图依赖 |
| --- | --- | --- | --- |
| 离线点云高精地图 | 稠密三维几何 | 专业离线生产 | 较强 |
| Lanelet2 矢量地图 | 车道语义与拓扑 | 离线生产和维护 | 较强 |
| 轻量语义地图 | 道路骨架与关键规则 | 离线或众包 | 中等 |
| 在线局部矢量地图 | 当前车道线、边界和路口元素 | 车端实时构建 | 较弱 |
| 局部占据地图 | 当前空间的空闲、占用和未知状态 | 车端实时构建 | 可独立，也可融合先验 |
| 隐式地图 | 神经网络内部空间特征 | 在线学习或时序维护 | 对传统地图较弱 |

## 传统高精地图到底包含什么

传统自动驾驶高精地图通常不是一张文件，也不是一幅非常清晰的底图，而是多种地图数据的组合。

以 Autoware 的架构为例，地图组件主要向系统提供：

- 表达道路语义的矢量地图；
- 表达稳定环境几何的点云地图；
- 在地理坐标与本地坐标之间转换所需的投影信息。

其中，点云地图主要服务 LiDAR 定位，也可以参与部分感知；矢量地图则服务路线规划、行为规划、交通灯检测和其他对象的轨迹预测。若系统有足够可靠的其他定位方法，点云地图并非绝对必需。

这三类数据必须落在一致的空间框架中：

```text
GNSS 经纬度
→ 地图投影
→ map 坐标系
→ 车辆 base_link 坐标系
→ 相机、LiDAR、毫米波雷达坐标系
```

只要坐标链条不一致，几何再精确也无法被算法正确消费。

## 点云地图：不是为了看，而是为了定位

点云地图保存道路周边相对稳定的三维结构，例如建筑立面、路缘、杆状物和地面形态。

典型定位过程是：

```text
预先构建的点云地图
+ 当前 LiDAR 扫描
→ 预处理与降采样
→ 选取车辆附近的地图分块
→ NDT / ICP 等点云配准
→ 估计车辆在 map 坐标系中的位姿
→ 与 GNSS、IMU、轮速等信息融合
→ 输出位置、方向、速度和不确定度
```

这里的输出不是渲染画面，而是一个带时间戳和协方差的车辆状态。

规划、感知和控制随后使用这个状态，把各自的数据放到同一个空间坐标系中。

### 为什么点云地图很“重”

点云高精地图可能覆盖大范围道路，每个点还携带三维坐标和可选的强度或颜色。车辆不可能把整个城市点云全部加载进内存。

工程上通常需要：

- 按空间范围分块；
- 建立分块元数据和索引；
- 根据当前位置加载局部点云；
- 对定位使用降采样版本；
- 在车辆移动后增量加载和卸载；
- 控制 CPU 内存、通信带宽和配准计算量。

Autoware 的地图加载器支持分割点云地图，并提供局部或差分加载能力。其本质与移动地图的瓦片调度相似：都在解决“只把当前位置附近真正需要的空间数据送进运行时”。

## 矢量语义地图：把道路变成可推理结构

点云告诉车辆环境几何长什么样，但无法单独完整表达交通规则。

矢量语义地图通常包含：

- 车道左右边界和中心线；
- 道路、路肩和可行驶区域；
- 停止线、人行横道和减速带；
- 交通灯、交通标志和检测区域；
- 限速、通行方向和转向限制；
- 车道之间的前后、左右、合流和分流关系。

它的核心不是“线画得很准”，而是空间语义和拓扑可以被算法查询。

```text
当前车辆位置
→ 匹配所在 Lanelet
→ 查询后继和相邻车道
→ 获取前方停止线、限速与交通灯
→ 构建路线走廊
→ 为行为规划提供约束
```

从 GIS 角度看，这是一张带有高精度几何、业务属性和网络拓扑的空间数据库。

## 一张地图怎样同时进入定位、感知和规划

地图不会先经过一个统一的“自动驾驶算法”，而是被多个模块以不同方式消费。

```text
                         ┌→ 定位
点云地图 ────────────────┤
                         └→ 感知辅助

                         ┌→ 基于地标或标线的定位
矢量语义地图 ────────────┼→ 感知与预测辅助
                         └→ 路线和行为规划
```

### 地图进入定位

定位模块可能使用：

- 点云与实时 LiDAR 的几何配准；
- 视觉地标或道路标线；
- GNSS 与地图投影；
- 车道几何对车辆位置的约束；
- IMU、轮速和方向盘信息。

最终输出通常是：

```text
pose(position, orientation)
velocity
acceleration
covariance
timestamp
map → base_link 的坐标变换
```

地图在这里相当于一个稳定空间参照系。

### 地图进入感知和预测

感知系统可以利用地图回答：

- 哪些区域应该是可行驶道路；
- 哪个交通灯控制当前车道；
- 哪些位置存在人行横道或停止线；
- 一个行人或车辆位于哪条车道附近；
- 动态对象可能沿哪些车道继续运动；
- 当前点云中的哪些部分属于静态地图背景。

地图不会替代传感器，因为施工、临时障碍和其他车辆不会可靠地存在于静态地图中。更常见的关系是：

```text
地图提供稳定先验与结构
传感器提供当前观测与变化
融合模块判断什么仍然可信
```

### 地图进入路径和行为规划

规划模块关心的不只是两点之间的最短距离，而是在道路规则和动态环境约束下如何行驶。

```text
起点与终点
→ 匹配到车道网络
→ 在拓扑图中选择路线
→ 构建当前路线走廊
→ 查询限速、停止线、路口和变道关系
→ 结合动态障碍生成行为决策
→ 生成几何轨迹与速度曲线
→ 交给控制模块
```

控制模块最终消费的是轨迹、曲率、速度和加速度目标，而不是地图本身。

## 渲染为什么只是旁路

自动驾驶系统通常仍然会显示地图：

- RViz 展示车道、点云、车辆和规划轨迹；
- 仿真平台展示传感器和算法状态；
- 远程监控平台展示车辆位置与告警；
- 车机显示导航路线和驾驶状态；
- 数据标注与地图编辑工具需要可视化。

但这些属于人类消费者。

算法主链路更准确地表示为：

```text
                        ┌→ 定位 → 车辆位姿
地图加载与空间查询 ─────┼→ 感知/预测 → 对象和运动状态
                        ├→ 规划 → 驾驶轨迹
                        └→ 可视化 → 屏幕像素
```

前三条支路直接影响车辆运行，最后一条负责解释和观察。即使关闭可视化，前三条仍然可以继续工作。

这就是自动驾驶作为“无渲染 GIS 链路”的经典意义：不是系统永远不画地图，而是空间数据无需经过渲染即可产生核心业务结果。

## 为什么行业开始讨论轻地图

传统高精地图给算法提供了丰富先验，但代价也很明显：

- 专业采集和制作成本高；
- 覆盖范围扩张慢；
- 道路变化后需要及时更新；
- 点云和详细几何占用大量存储与传输；
- 地图版本必须与车辆算法兼容；
- 现实与地图不一致时可能误导算法；
- 大规模运营需要复杂的数据闭环。

于是出现“轻地图”思路。

它不是一个统一格式，也不只是把文件压缩得更小，而是有意识地降低车辆对重型高精先验的依赖。

### 轻地图可能保留什么

不同方案的轻量化位置不同，可能只保留：

- 道路中心线与拓扑；
- 路口和道路连接关系；
- 关键交通规则；
- 粗粒度车道数量和方向；
- 少量稳定定位特征；
- 导航路线或道路级地图；
- 无法由实时传感器可靠推断的先验。

其余内容由车端感知补充：

```text
轻量道路骨架
+ 当前相机和 LiDAR 观测
→ 识别真实车道线与边界
→ 判断施工、障碍和临时变化
→ 构建当前局部道路结构
→ 进入定位和规划
```

### “轻”减轻了什么

轻量化可能发生在不同层面：

| 轻量化对象 | 具体做法 | 转移出去的压力 |
| --- | --- | --- |
| 数据量 | 去除稠密点云，只保留关键特征 | 转向视觉或其他定位方式 |
| 语义密度 | 只保留骨架与关键规则 | 转向实时道路理解 |
| 几何精度 | 使用较粗道路或车道先验 | 转向传感器细化 |
| 覆盖维护 | 依赖众包或在线变化检测 | 转向数据闭环 |
| 车端依赖 | 地图只作提示而非硬约束 | 转向算法鲁棒性 |

因此轻地图并不是“免费获得更简单系统”。地图侧减少的责任，会转移给感知、定位、融合和不确定性处理。

## 语义地图究竟是什么

“语义”描述的是地图对象在道路系统中的含义，而不是地图的重量和生产时间。

一条几何线只有坐标时，只是一条线；当系统知道它是左车道边界、禁止跨越、属于某条 Lanelet，并与前方停止线和交通灯关联时，它才具有可以进入驾驶决策的语义。

语义地图可能包含：

```text
几何：位置、形状、方向
类别：车道线、路缘、停止线、人行横道
属性：颜色、虚实、限速、通行方向
关系：相邻、连接、控制、属于
规则：可否变道、让行、停车和优先权
```

因此，下面几种都可以叫语义地图：

- 专业离线制作的高精 Lanelet2 地图；
- 只保留关键道路规则的轻量地图；
- 车辆实时识别的局部矢量地图；
- 感知网络输出的车道与路口拓扑。

## 在线语义地图：车辆边开边构建局部道路

在线地图构建试图根据当前传感器，在车辆附近实时恢复结构化道路元素。

典型流程是：

```text
多相机图像 / LiDAR
→ 特征提取
→ 视角变换或 BEV 表示
→ 检测车道线、道路边界、人行横道等实例
→ 把实例表达为折线、曲线或多边形
→ 推断连接和邻接关系
→ 与历史帧融合
→ 形成车辆周围的局部矢量语义地图
```

HDMapNet、VectorMapNet、MapTR、StreamMapNet 等研究虽然模型结构不同，但共同变化是：地图不再完全是车辆出发前安装的静态文件，而可以成为感知系统的实时输出。

### 在线地图解决了什么

- 减少对大范围预制高精地图的依赖；
- 能看见近期施工和道路变化；
- 适应尚未完成专业制图的区域；
- 让道路结构直接来自当前传感器；
- 可以在局部范围内持续刷新。

### 在线地图又带来了什么问题

- 遮挡、雨雾和光照会影响识别；
- 传感器视野有限，远处结构不完整；
- 单帧输出容易抖动和断裂；
- 拓扑关系比检测几条线更难；
- 结果带有概率和不确定性；
- 当前看不见的交通规则可能无法推断；
- 推理延迟必须满足规划周期。

离线地图把不确定性放在采集、生产和更新环节；在线地图则把不确定性直接带入车辆运行时间。

## 局部地图为什么需要时序记忆

车辆当前帧只能看到有限范围。前一秒已经看见的车道，可能在下一秒被大车遮挡。

因此，在线地图往往不是每帧从零开始，而是维护局部时序状态：

```text
上一帧局部地图
→ 根据车辆运动变换到当前坐标
+ 当前传感器新观测
→ 数据关联与更新
→ 保留仍可信的历史结构
→ 删除过期或冲突对象
→ 输出新的局部地图
```

这与 GIS 的增量更新非常相似：系统需要对象 ID、空间关联、版本或时间戳、冲突处理和更新边界。

不同的是，在线地图的更新周期可能是毫秒或秒级，且每个对象都带有观测不确定性。

## 占据地图：不先识别名字，先判断能不能走

语义矢量地图擅长表达车道和规则，但规划还需要知道当前空间是否被障碍占用。

占据地图把周围空间划分为二维网格、三维体素或 BEV 单元，并估计：

```text
空闲
占用
未知
```

更复杂的占据表示还可能包含：

- 语义类别；
- 运动状态；
- 高度；
- 可见性；
- 未来占据概率。

典型链路是：

```text
相机 / LiDAR / 雷达
→ 坐标统一
→ 估计空间占据
→ 融合静态可行驶区域和动态对象
→ 生成局部 Costmap 或 Occupancy Grid
→ 规划搜索可通过空间
```

占据地图和语义地图不是互相替代：

```text
语义地图回答：这里是什么道路结构、受什么规则约束
占据地图回答：当前哪些空间空闲、占用或未知
```

两者结合，规划既知道“理论上可以走哪里”，也知道“此刻实际上能否通过”。

## 特征地图：地图可以只保存定位需要的东西

如果点云地图主要用于定位，就不一定要保存完整稠密环境。

特征地图可以只记录稳定、可重复观测的元素，例如：

- 视觉关键点和描述子；
- 车道标线或杆状地标；
- 建筑边缘和路缘；
- LiDAR 反射强度特征；
- 神经网络提取的定位特征。

定位过程变为：

```text
当前传感器提取特征
+ 地图中的稳定特征
→ 特征匹配与几何约束
→ 估计车辆位姿
```

它减少地图体积，却对特征的稳定性、跨天气和跨传感器泛化提出更高要求。

## 隐式地图与“无图”到底意味着什么

显式地图会输出可以直接检查的对象：点、线、面、体素、车道和拓扑。

隐式地图则可能把空间信息保存在神经网络特征中：

```text
历史多帧传感器
→ BEV / 记忆特征
→ 时序融合
→ 内部空间表示
→ 对象、占据、车道或驾驶轨迹
```

系统未必生成一个传统 Lanelet 文件，但内部特征仍然编码了位置、方向、邻近和可行驶空间。

所谓“无图”通常更准确地理解为：

> 不依赖预先制作并持续下发的传统高精地图，而不是完全不使用空间结构和历史先验。

很多“无图”方案仍可能使用：

- 普通导航地图与目标路线；
- GNSS 和道路级拓扑；
- 历史帧形成的局部空间记忆；
- 训练数据中学到的道路结构先验；
- 实时生成的 BEV 或占据表示。

因此，地图从文件消失，不等于 GIS 问题消失。它只是从显式数据产品移动到了模型、特征和在线推理过程。

## 真实系统更可能是混合架构

传统高精地图、轻地图和在线地图不一定互相彻底取代。更现实的方案是按可靠性和成本分工。

```text
道路级导航地图
→ 提供全球覆盖和目标路线

轻量语义先验
→ 提供关键拓扑、路口和交通规则

在线局部语义地图
→ 恢复当前车道线、边界与道路结构

占据地图
→ 表达当前障碍和未知空间

传感器与时序记忆
→ 发现变化并补足局部细节
```

规划模块最终消费的可能不是某一张权威地图，而是经过融合后的当前世界模型。

### 地图冲突时相信谁

混合系统必须处理冲突：

- 地图说有三条车道，传感器只看到两条；
- 地图允许直行，施工护栏已经封闭道路；
- 在线模型识别出一条车道线，但置信度很低；
- GNSS 位置和车道匹配结果不一致；
- 静态地图版本已经过期；
- 其他车辆上传的变化尚未完成验证。

系统需要显式表达：

```text
来源
时间
版本
置信度
空间范围
有效期限
冲突状态
```

这和传统 GIS 的数据质量、血缘和时效管理是同一个问题，只是安全和实时性要求更高。

## 无论地图多轻，都绕不开坐标系统

自动驾驶同时存在多个坐标框架：

```text
地理坐标：经度、纬度、高程
地图坐标：投影后的全局或区域坐标
odom 坐标：车辆运行过程中的连续局部坐标
base_link：车辆本体坐标
sensor frame：相机、LiDAR、雷达坐标
局部 BEV / grid：模型和规划使用的局部空间
```

数据进入算法之前，必须知道：

- 坐标属于哪个 frame；
- 时间戳对应哪一时刻；
- 外参和车辆姿态是否有效；
- 变换链是否连续；
- 地图投影与 GNSS 是否一致；
- 局部原点何时变化；
- 不确定度怎样传播。

一条在线车道线识别得再准确，如果被放进错误坐标系，也无法和路线、障碍及车辆状态对齐。

## 地图怎样局部加载和快速查询

即便采用轻地图，车辆也不应该每次遍历整张路网。

运行时通常需要：

```text
根据车辆位置确定当前分块
→ 加载前方路线走廊和周边缓冲区
→ 建立局部车道与对象索引
→ 查询最近车道、前方停止线和相邻关系
→ 车辆移动后增量加载与卸载
```

常见查询包括：

- 点到车道的最近距离；
- 当前点位于哪个可行驶面；
- 前方一定距离内有哪些监管元素；
- 哪些车道与当前车道连接；
- 动态对象可能落在哪条车道；
- 路线走廊与障碍区域是否相交；
- 当前位置附近有哪些定位特征。

这些依然是空间索引、几何计算和网络拓扑问题。

## 一次路口通行的完整无渲染链路

假设车辆即将进入一个有交通灯和人行横道的十字路口。

### 地图与路线准备

```text
道路级导航路线
→ 确定目标路口和转向方向
→ 加载路口附近的轻量或高精语义地图
→ 查询当前车道、后继车道和监管元素
```

### 定位

```text
GNSS + IMU + 轮速
+ 点云地图或定位特征地图
→ 输出车辆位姿与不确定度
→ 把车辆、传感器和地图统一到当前坐标框架
```

### 在线道路理解

```text
多相机 / LiDAR
→ 构建 BEV 特征
→ 识别车道线、道路边界、停止线和人行横道
→ 与离线语义先验进行关联
→ 标记一致、变化和不确定部分
```

### 感知与占据

```text
识别车辆、行人和非机动车
→ 估计位置、速度和未来轨迹
→ 构建当前局部占据状态
→ 判断人行横道和冲突区域是否被占用
```

### 行为与轨迹规划

```text
路线方向
+ 交通灯状态
+ 停止线与路口规则
+ 动态对象预测
+ 当前占据地图
→ 判断停车、等待或通过
→ 生成穿过路口的轨迹与速度曲线
→ 发送给控制模块
```

整个过程都不要求地图先变成屏幕像素。可视化模块可以并行订阅这些结果，画出车道、对象和轨迹，供工程师观察。

## 地图错误怎样传导成驾驶风险

自动驾驶地图问题不会只表现为“图层偏了”。它可能沿算法链路继续放大。

| 地图问题 | 直接影响 | 可能传导结果 |
| --- | --- | --- |
| 点云地图与现实变化过大 | 配准不稳定 | 定位漂移或失败 |
| 投影或外参错误 | 地图与传感器错位 | 对象关联和规划错误 |
| 车道拓扑断裂 | 路线搜索中断 | 无法生成有效路线 |
| 停止线关联错误 | 交通规则查询错误 | 停车位置或通行决策异常 |
| 限速和方向过期 | 规则先验错误 | 不合理速度或路线 |
| 在线车道识别抖动 | 局部结构不稳定 | 轨迹左右摆动 |
| 占据地图漏检 | 可通行性误判 | 规划进入真实障碍区域 |
| 地图版本混用 | 模块空间认知不同 | 难以复现的系统性冲突 |

因此地图质量不能只看几何误差，还要检查语义、拓扑、时效、覆盖范围以及算法可用性。

## 高精、轻量和在线方案怎样比较

| 维度 | 传统高精地图 | 轻地图 | 在线局部语义地图 | 隐式 / 弱传统地图方案 |
| --- | --- | --- | --- | --- |
| 预先生产成本 | 高 | 中或低 | 较低 | 较低 |
| 车端实时计算 | 中 | 较高 | 高 | 很高 |
| 覆盖扩展 | 较慢 | 较快 | 随车辆运行 | 随车辆运行 |
| 稳定先验 | 丰富 | 保留关键部分 | 受当前观测限制 | 隐含在模型和历史中 |
| 道路变化响应 | 依赖更新链路 | 地图与感知共同处理 | 可以即时观察 | 可以即时观察 |
| 可解释性 | 较强 | 较强 | 输出可显式检查 | 通常较弱 |
| 极端天气与遮挡 | 地图仍可提供先验 | 仍有部分先验 | 感知可能退化 | 模型可能退化 |
| 主要风险 | 过期与维护成本 | 先验不足 | 短视、抖动和不确定性 | 泛化、验证和可解释性 |

不存在脱离业务约束的绝对优胜者。

封闭园区、固定线路和港口车辆可能更适合稳定高精地图；大范围城市开放道路可能更重视轻地图与在线感知；量产系统也可能长期采用多种表示并存的混合架构。

## 它为什么仍然是 GIS

地图从文件变成在线网络输出，甚至进入神经网络内部后，传统 GIS 名称可能不再出现，但核心空间问题仍然存在。

| GIS 能力 | 自动驾驶中的表现 |
| --- | --- |
| 空间数据模型 | 车道、边界、点云、地标、体素和占据单元 |
| 坐标与投影 | 地理、地图、车辆、传感器和 BEV 坐标转换 |
| 空间索引 | 加载附近地图，查询最近车道和监管元素 |
| 几何计算 | 距离、投影、相交、包含、曲率和边界判断 |
| 拓扑关系 | 车道连接、邻接、合流、分流与路口网络 |
| 分块与调度 | 点云和矢量地图的局部、差分加载 |
| 时空数据融合 | 离线先验、当前观测和历史状态融合 |
| 数据质量 | 精度、完整性、时效、置信度和适用范围 |
| 版本与血缘 | 地图、模型和车辆软件之间的一致性 |

自动驾驶不是离开了 GIS，而是把 GIS 从“给人看的地图”推进成“给算法使用的空间基础设施”。

## 回到 GIS 系统的五种责任

把它放回数据、处理、分析、服务与渲染五种责任，可以看到渲染并不在主链终点。

```text
数据
→ 点云、车道语义、定位特征、占据状态和传感器观测

处理
→ 标定、投影、分块、降采样、在线矢量化和时序融合

分析
→ 定位配准、空间关联、拓扑查询、路线与轨迹规划

服务
→ 地图发布、版本更新、局部加载以及 ROS 2 消息和服务

渲染
→ RViz、仿真、车机和监控平台中的可选观察支路
```

这条链路最终产生的是车辆位姿、对象状态、道路结构和驾驶轨迹，而不是一张地图截图。

## 最后总结

自动驾驶地图的演进，不应被理解成一个新名词简单替代旧名词。

更准确的变化是：

```text
地图表达
从稠密几何和完整语义
扩展到轻量骨架、在线矢量、占据和隐式特征

地图生产
从专业离线制图
扩展到众包更新、车端在线构建和时序维护

地图依赖
从强依赖预制高精地图
走向轻先验、实时感知与混合世界模型
```

无论采用哪条路线，车辆仍然需要解决同一组空间问题：我在哪里，周围空间怎样组织，哪些道路相互连接，什么区域可以通行，当前观测与既有先验是否一致，以及下一条轨迹是否满足几何和规则约束。

这些问题不需要先被渲染成像素，却完整保留了 GIS 的数据模型、坐标、索引、几何、拓扑、时空融合和质量管理能力。

因此，自动驾驶中的 GIS 可以这样概括：

> 地图不再只是被车辆显示，而是以显式或隐式空间表示进入定位、感知和规划，成为车辆理解世界并生成行动的计算基础。

下一篇继续沿自动驾驶深入生产侧：[矿区无人驾驶地图平台：从测绘采集、编辑质检到车辆发布](/posts/mining-autonomous-driving-map-platform)。届时会看到，点云、道路和作业区怎样经过编辑、质检、版本管理与编译发布，成为车辆可以稳定消费的地图数据产品。
