# 空间索引：地图为什么能从百万要素中快速找到附近对象

<p class="post-meta">2026-10-12 · GIS 核心概念 · 空间索引与查询原理 · 约 18 分钟</p>

在地图上框选一个区域、查找车辆附近的道路，或者判断哪些建筑落入淹没区时，我们很容易把问题理解成一句 SQL 或一个 API：

```sql
SELECT *
FROM roads
WHERE ST_Intersects(geom, :search_area);
```

但如果道路表里有几百万条记录，数据库真的会把每条道路都拿出来，与查询区域做一次完整的几何相交计算吗？通常不会。

空间查询之所以快，不是因为精确几何计算突然变得便宜，而是因为系统先用空间索引排除绝大多数“不可能命中”的对象，只把少量候选交给精确算法。

这篇文章从这个核心思想出发，解释空间索引到底保存什么、为什么允许假阳性、规则网格和 R-Tree 有什么差别，以及自动驾驶地图里的车道索引如何落地。

## 没有索引时，计算机只能逐个询问

假设地图里有 100 万条道路，用户只框选了屏幕右上角的一小块区域。最直接的算法是遍历全部道路：

```ts
const result = []

for (const road of roads) {
  if (intersects(road.geometry, viewport)) {
    result.push(road)
  }
}
```

这种方法叫全量扫描。它没有错，而且数据很少时往往已经足够好。问题在于，数据量每增加一倍，需要检查的对象也近似增加一倍。

更麻烦的是，`intersects` 并不只是比较几个数字。真实几何可能包含数百甚至数万个顶点，还可能带洞、多部件和复杂边界。对所有对象直接做精确计算，会把大量时间浪费在明显不相关的数据上。

![全量扫描与空间索引查询对比](/images/spatial-index/full-scan-vs-index.svg)

空间索引改变的不是最后那个“是否相交”的定义，而是参与精确判断的对象数量：

```text
全量扫描：100 万条道路 → 100 万次精确判断
空间索引：100 万条道路 → 数百个候选 → 数十个真实结果
```

候选数并不总是这么理想，但方向始终相同：先缩小范围，再做昂贵计算。

## 索引保存的不是完整几何，而是空间摘要

### 最常见的摘要：最小外接矩形

空间对象可以是弯曲道路、不规则地块或复杂建筑。直接把完整几何塞进索引，会让索引本身变得庞大而难以比较。因此，许多空间索引先为对象保存一个更简单的摘要——最小外接矩形：

```text
Minimum Bounding Rectangle
MBR / Bounding Box / Envelope
```

二维 MBR 只需要四个值：`minX, minY, maxX, maxY`。

如果对象的 MBR 与查询框完全不相交，那么真实几何一定不相交，可以安全排除。

如果两个 MBR 相交，真实几何却不一定相交。例如两条弯曲道路的外接矩形可能重叠，但道路本身没有碰到。此时索引只能把对象列为候选，不能直接宣布命中。

这就形成空间查询最重要的两阶段结构。

## 两阶段查询：粗过滤与精确判断

![空间查询的粗过滤与精确判断](/images/spatial-index/two-stage-query.svg)

第一阶段通常叫粗过滤、索引过滤或候选检索：

```text
输入查询范围
→ 使用 MBR、网格编号或树节点快速比较
→ 得到可能命中的候选对象
```

第二阶段叫精确过滤或几何复核：

```text
读取候选对象的真实几何
→ 执行 Intersects / Contains / Distance 等精确计算
→ 得到最终结果
```

用伪代码表示：

```ts
const candidates = spatialIndex.search(queryBounds)
const result = candidates.filter(feature =>
  intersects(feature.geometry, queryGeometry)
)
```

这里有两个非常关键的概念。

### 假阳性可以接受

索引说“它可能命中”，精确计算后发现没有命中，这叫假阳性。假阳性只会让后续多做一点工作，不会让最终结果出错。

### 假阴性通常不可接受

索引说“它不可能命中”，但真实几何其实命中了，这叫假阴性。对象已经在第一阶段被排除，后面再精确的算法也找不回来。

因此，大多数空间索引遵守这样的工程约束：

> 宁可多返回少量候选，也不能漏掉真正应该参与计算的对象。

## 为什么普通 B-Tree 不能直接解决二维邻近问题

数据库里的普通索引通常擅长一维有序值，例如年龄、时间和编号。B-Tree 可以利用这种顺序快速查找某个值或连续区间。

空间坐标却至少有两个维度。只按 X 排序时，X 很接近的对象在 Y 上可能相隔几千公里；只按 Y 排序也有同样问题。把二维位置简单压成一个数字，还会面临“编码接近不一定空间接近、空间接近也可能跨编码边界”的情况。

GeoHash、Morton Code 等空间填充曲线确实可以把多维位置映射成一维编码，并借助普通索引查询，但它们需要额外处理编码边界和多个区间。它们是有效方案，却不是“给 X、Y 各建一个普通索引”那么简单。

空间索引的共同目标，是让数据结构理解二维或多维中的邻近与覆盖。

## 规则网格：把空间切成可直接寻址的格子

最容易理解的空间索引是规则网格。先把工作区域切成固定大小的正方形，再记录每个格子可能包含哪些对象：

```text
cell(12, 8) → lane 3, lane 7
cell(13, 8) → lane 3
cell(14, 8) → lane 3, lane 9
```

查询一个位置时，可以直接根据坐标计算行列号：

```ts
const col = Math.floor((x - originX) / cellSize)
const row = Math.floor((y - originY) / cellSize)
```

查询一个圆形或矩形范围时，则访问它覆盖的全部格子，合并候选并去重。

![车道中心线写入规则网格](/images/spatial-index/grid-lane-index.svg)

### 网格索引的优点

- 结构直观，容易实现、序列化和调试；
- 坐标到格子编号可以直接计算，查询路径短；
- 静态地图可提前编译，车端只读取紧凑数组；
- 数据布局连续时，对 CPU 缓存很友好；
- 网格边界固定，结果容易保持确定性。

### 网格索引的代价

- 单元过大时，每个格子候选太多，粗过滤效果差；
- 单元过小时，一个对象跨越很多格子，引用数量和去重成本上升；
- 数据分布极不均匀时，繁华区域很拥挤，空旷区域又浪费格子；
- 超长对象可能被重复写入大量单元；
- 查询半径较大时，需要访问很多格子。

网格大小并不存在脱离数据和业务的“最佳值”。它需要同时考虑对象尺度、密度、查询半径、内存和更新频率。

## R-Tree：用层级矩形逐层排除空间

R-Tree 不把空间切成尺寸固定的格子，而是把邻近对象的 MBR 组合成更大的 MBR，再逐层组成一棵平衡树。

![R-Tree 的层级包围盒结构](/images/spatial-index/r-tree-hierarchy.svg)

查询时从根节点开始：

1. 检查查询范围与哪些上层 MBR 相交；
2. 只进入相交的分支；
3. 继续检查更小的子节点；
4. 到达叶子后得到候选对象；
5. 使用真实几何完成精确判断。

如果查询区域只落在树的一小部分，其他整棵分支都可以跳过。

R-Tree 很适合矩形、道路、地块等范围不同的对象，也支持动态插入和删除。PostGIS 常用的 GiST 空间索引可以承载类似 R-Tree 的“包围盒逐层过滤”思想。

但 R-Tree 也不是魔法。节点 MBR 可能互相重叠，查询就要进入多个分支；对象插入顺序、节点分裂策略和数据分布都会影响树的质量。静态只读场景还常使用批量构建、紧凑布局的 Packed R-Tree 或 Flatbush 一类结构。

## 规则网格、四叉树和 R-Tree 怎样选择

| 结构 | 空间怎样组织 | 更适合的场景 | 主要代价 |
|---|---|---|---|
| 规则网格 | 固定大小单元 | 范围明确、对象尺度接近、静态或高频点查询 | 网格尺寸敏感，分布不均时效率下降 |
| 四叉树 | 拥挤区域递归四分 | 点或小对象密度差异明显、空间范围稳定 | 深度和边界处理更复杂 |
| R-Tree | 邻近 MBR 分层聚合 | 通用矢量对象、数据库动态更新 | 节点重叠与维护成本 |
| Packed R-Tree | 静态批量构建的紧凑 R-Tree | 只读地图包、浏览器和车端发布数据 | 更新通常需要重建 |
| GeoHash / H3 / S2 | 空间单元编码 | 分布式聚合、分区、邻域统计 | 边界、层级和精确几何仍需额外处理 |

选择结构时，不应只问“哪一种最快”，而应问：

```text
数据是静态还是频繁更新？
对象是点、短线、长线还是大面？
分布均匀吗？
典型查询是点附近、视口范围还是大面积叠加？
索引放在数据库、服务端、浏览器还是车端？
允许占用多少内存和磁盘？
```

同一套系统也可能同时使用多级索引：数据库用 GiST，瓦片服务按 Tile 分区，浏览器对当前瓦片中的要素再建立轻量索引。

## 自动驾驶地图里的车道空间索引

自动驾驶地图中，很多运行时问题都从“先找附近候选”开始：

- 车辆当前位置附近有哪些 Lane；
- 定位点最可能匹配哪条车道中心线；
- 给定搜索半径内有哪些停止线、标志或路口对象；
- 当前局部规划范围需要加载哪些地图块。

地图中的 `LaneId` 可以帮助按身份直接定位一条车道，但无法回答“这个坐标附近有哪些车道”。这正是空间索引的职责。

### 一个适合教学型车端地图包的方案

以局部 ENU 平面中的车道中心线为例，可以在编译阶段建立规则网格：

```text
坐标系：局部 ENU 的 X/Y 平面
单位：米
网格：20 m × 20 m
覆盖扩张：车道中心线包围盒四周各 1 m
索引值：当前地图包中的 LaneIndex
```

编译每条车道时：

1. 读取中心线点列；
2. 对每一条折线段计算 XY 轴对齐包围盒；
3. 找到包围盒覆盖的全部网格单元；
4. 对同一车道的命中单元排序去重；
5. 把 `LaneIndex` 写入各单元的候选列表。

用线段包围盒入格，会让斜线附近少数没有真正相交的格子也包含这条车道。这是假阳性，但它保证所有真正与线段相交的格子都不会漏掉。

### 为什么还要给覆盖范围留出余量

中心线是零宽度线，但实际查询往往带搜索半径。编译时增加少量 padding，可以吸收量化、边界和小范围搜索带来的脆弱性。

这并不意味着查询时只看当前格子就足够。假设车辆距离格子边界 0.2 米，搜索半径是 5 米，那么候选车道完全可能位于相邻格子。正确做法是查询搜索范围覆盖的所有单元。

### 候选车道不等于匹配结果

从网格得到 `LaneIndex` 以后，还要使用真实中心线和业务条件继续判断：

```text
网格索引候选
→ 点到中心线的精确距离
→ 车辆航向与车道方向差
→ 车道宽度或可行驶区域
→ 车道类型、方向和通行规则
→ 最终地图匹配结果
```

如果只选“当前格子里的第一条车道”，平行车道、匝道、上下层道路和路口区域都会迅速暴露问题。

### 为什么索引不能跨地图包复用

为了紧凑，车端索引常保存数组下标 `LaneIndex`，而不是较大的稳定业务 ID。地图重新编译后，Lane 数组顺序可能改变，同一个下标便可能指向另一条车道。

因此：

> 空间索引必须与生成它的地图数据一起发布、校验和切换，不能把旧索引搭配新地图。

这也是地图包通常带版本号、区段校验和与整体原子切换机制的原因之一。

## 空间索引最容易踩的坑

### 只做包围盒查询，不做精确复核

MBR 相交只代表“可能相交”。如果业务需要真实的 `Intersects`、点到线距离或点在面内判断，必须继续计算真实几何。

### 用经纬度直接当作平面米制坐标

经纬度的单位是度，不是米；同样的经度差在不同纬度代表的地面距离不同。局部距离和规则网格通常应在合适的投影坐标或局部 ENU 坐标中建立，并明确单位与适用范围。

### 查询半径只访问中心点所在单元

搜索圆可能跨越相邻单元。只查一个格子会产生真正的漏检，也就是最危险的假阴性。

### 单元边界规则不一致

点恰好落在网格线上时，编译器和查询器必须采用相同规则，例如内部边界统一归到右侧或上侧单元，最大边界钳制到最后一行或列。否则同一点可能在写入和读取时得到不同格子编号。

### 索引存在，就以为查询一定使用了它

数据库查询还取决于统计信息、数据分布、选择率、函数写法和查询计划。空间表已经建索引，不代表每条 SQL 都会走索引。工程中仍要查看 `EXPLAIN ANALYZE`。

### 忘记更新成本

插入、删除或修改几何时，索引也要同步更新。静态发布包适合离线重建；实时编辑数据库则要接受写入放大、页分裂和维护开销。

## 怎样验证一个空间索引没有漏检

性能测试之前，先验证正确性。一个实用的测试思路是：

1. 构造水平、垂直、斜向和跨多格子的线；
2. 对每条线段密集采样；
3. 根据采样点计算所在网格；
4. 断言对应格子的候选中始终包含该对象；
5. 专门覆盖内部网格线、四角和最大边界；
6. 对不同半径查询，与全量扫描结果对照；
7. 允许候选多于精确结果，但不允许精确结果缺失。

可以把核心不变量写成：

```text
exactResults(query) ⊆ indexCandidates(query)
```

在此基础上，再测量：

- 平均和最坏候选数量；
- 查询耗时与 P95/P99 延迟；
- 索引文件大小和内存占用；
- 不同网格尺寸或节点容量的效果；
- 数据更新和索引重建成本。

一个返回很快却会漏掉道路的索引没有工程价值；一个永不漏检但每次返回全表的索引也没有加速价值。空间索引设计就是在正确性约束下，尽量提高过滤能力并控制存储与维护成本。

## 总结

空间索引并不直接替代几何计算。它真正做的是：

```text
用简单、便宜的空间摘要
快速排除绝大多数不可能对象
再把少量候选交给精确算法
```

理解这一点以后，规则网格、四叉树、R-Tree、GeoHash 和数据库 GiST 就不再是一堆孤立名词。它们是在不同数据分布、查询模式和运行环境下，对同一个问题给出的不同答案。

对自动驾驶地图而言，空间索引也只是候选层。网格可以快速找出附近 Lane，但最终匹配仍然需要距离、航向、车道几何和交通规则共同决定。

下一次看到“地图在百万要素中瞬间找到附近对象”时，可以把它拆成一条清晰链路：

> **空间分区或层级包围盒 → 候选集合 → 真实几何计算 → 业务语义判断。**
