# 离线处理链路和在线请求链路究竟有什么不同

<p class="post-meta">2026-07-20 · GIS 全链路 · 系统架构 · 约 17 分钟</p>

同样是计算积水区内受影响的道路，一个系统可能每天凌晨提前算好，用户打开地图时直接读取结果；另一个系统可能等用户画出积水范围后，再根据当前道路数据即时计算。

两种方案都可能使用坐标转换、空间索引和 `ST_Intersects`，最后也都能把受影响道路显示成红色。但它们面对的工程问题完全不同。

提前计算时，我们关心一批数据能否完整处理、失败后能否重跑、结果能否复现；请求到来后再计算时，我们关心用户要等多久、并发上来是否会拖垮系统、缓存是否正确、超时后怎样降级。

这就是离线处理链路和在线请求链路最核心的区别：

> 离线与在线不取决于有没有连接互联网，而取决于计算发生在消费者提出请求之前，还是发生在请求到来之后。

云服务器上的夜间任务仍然是离线处理；手机在没有网络时根据一次点击即时查询本地地图，仍然具有在线请求式处理的特点。这里的“在线”，强调的是请求时执行，而不是网络连接状态。

## 先用一张表建立直觉

| 维度 | 离线处理链路 | 在线请求链路 |
| --- | --- | --- |
| 触发方式 | 定时、批量、人工或数据更新 | 用户请求、设备请求或实时事件 |
| 输入 | 相对确定的数据快照 | 请求参数与当前可用数据 |
| 主要目标 | 吞吐量、完整性、可重复生产 | 低延迟、高并发、稳定响应 |
| 输出 | 文件、瓦片、索引、成果表和模型 | 查询结果、地图图片、接口响应和任务状态 |
| 时间尺度 | 秒、分钟、小时甚至更长 | 通常要求毫秒到秒级反馈 |
| 失败处理 | 重试、断点续跑、重新执行 | 超时、限流、降级和快速失败 |
| 数据状态 | 强调批次、版本和血缘 | 强调新鲜度、一致性和权限 |
| 资源使用 | 可以排队、并行和集中调度 | 必须应对不可预测的请求峰值 |
| 结果复用 | 通常持久化并被多次消费 | 可能即时返回，也可能进入缓存 |
| 核心指标 | 吞吐量、成功率、质量和生产耗时 | P95/P99 延迟、QPS、错误率和可用性 |

可以把两者的性能目标压缩成一句话：

> 离线链路主要优化单位时间能可靠生产多少成果；在线链路主要优化一个请求能否在有限时间内稳定返回。

不过，这并不意味着真实系统必须在两者之间二选一。大多数 GIS 产品会把两条链路组合起来。

## 同一个空间问题的两种实现

继续使用上一篇的场景：系统需要找出暴雨积水范围内受影响的道路，并在地图中高亮。

### 离线方案：提前生产道路风险成果

如果积水预测每天更新一次，系统可以在数据到达后批量计算：

```text
道路数据快照 + 积水预测快照
→ 校验输入版本
→ 统一坐标
→ 修复几何
→ 建立或更新空间索引
→ 执行道路与积水区相交分析
→ 生成道路风险等级
→ 质量检查
→ 写入成果表并生成瓦片
→ 发布新版本
```

用户打开地图时，在线服务只需要读取已经算好的风险字段或瓦片。

它的优势很直接：

- 昂贵计算不会进入用户等待时间；
- 同一份结果可以被大量用户重复使用；
- 生产过程有明确的数据批次，容易追踪和复现；
- 可以在发布前完成完整的质量检查；
- 在线系统的资源消耗更稳定。

代价也同样明显：

- 用户看到的是最近一次生产结果，不一定是最新状态；
- 道路或积水数据变化后，需要重新计算受影响部分；
- 预先无法穷举所有临时范围、阈值和组合条件；
- 全量成果可能消耗大量存储空间和生产时间。

### 在线方案：根据当前请求即时计算

如果用户可以在地图上任意绘制积水范围，系统可能采用请求时分析：

```text
用户提交范围与筛选条件
→ 身份、权限和参数校验
→ 查找当前道路数据版本
→ 空间索引预筛选
→ 精确相交判断
→ 业务属性过滤
→ 结果裁剪与序列化
→ 返回道路要素
→ 客户端高亮显示
```

它的优势是灵活和及时：

- 每个请求可以携带不同范围和业务条件；
- 能够使用请求发生时的当前数据；
- 不必提前存储所有可能的组合结果；
- 适合探索式查询和交互式分析。

相应的问题是：

- 空间计算直接占用请求的延迟预算；
- 同一类昂贵计算可能被重复执行；
- 高并发会争抢数据库、CPU、内存和网络资源；
- 慢查询、异常几何和超大返回结果可能拖垮服务；
- 缓存、权限和数据一致性必须在请求链路中同时处理。

两个方案没有绝对高下。它们只是在“结果新鲜度、查询灵活性、计算成本和响应速度”之间选择了不同位置。

## 离线处理链路真正负责什么

离线链路不是简单地运行一个脚本。只要它开始稳定生产业务成果，就需要面对一套完整的工程责任。

### 1. 固定输入范围和版本

离线任务首先要知道自己处理的是哪一批数据。

```text
道路版本：road_2026_07_20
积水预测：flood_2026_07_20_0800
处理规则：risk_model_v3
```

如果执行过程中输入数据不断变化，同一个任务的不同分区可能使用不同版本，最后得到一份无法解释的混合成果。

因此，离线生产通常需要数据快照、版本号、时间范围或明确的增量边界。所谓可复现，首先意味着以后能够回答：这份成果由哪些输入和规则生成？

### 2. 校验、转换和组织数据

原始数据进入分析前，往往要经历坐标转换、几何修复、字段映射、裁剪、简化、重采样和索引构建。

这些步骤可以组成稳定的数据管线。GDAL 的 pipeline 模型就是“读取数据—执行多个步骤—写出结果”的典型表达；中间结果可以流式传递，也可以为了性能或复用而持久化。

是否落盘不是越少越好。对于代价高、后续会重复使用或需要检查的阶段，中间成果反而可以成为清晰的恢复点。

### 3. 批量计算和质量检查

离线任务可以使用更长时间完成全量空间叠加、栅格计算、点云处理或网络模型计算，但“最终成功”不能只看进程退出码。

还要验证：

- 输入数量与输出数量是否合理；
- 几何是否有效；
- 坐标范围和单位是否正确；
- 是否出现异常空值或极端值；
- 不同分区之间是否遗漏或重复；
- 新结果与上一版本相比是否发生异常跳变。

离线链路的质量检查发生在成果进入在线系统之前，它是阻止错误批量扩散的重要关口。

### 4. 幂等、重试与断点续跑

处理几百 GB 影像或几千万个要素时，任务失败后从头再来可能非常昂贵。

离线任务通常需要：

- 同一批次重复执行不会产生重复和污染；
- 能够从成功的分区或阶段继续；
- 失败记录包含输入、参数和错误位置；
- 临时成果与正式成果隔离；
- 只有全部检查通过，才把新版本切换为可用状态。

这也是离线链路与一次性脚本的分界：脚本完成某次操作，生产链路要保证它可以长期、重复、可追踪地运行。

### 5. 发布可消费的成果

离线任务的终点不是“文件生成成功”，而是成果被下游稳定消费。

它可能输出：

- GeoPackage、GeoTIFF、COG、MBTiles 或其他文件；
- PostGIS 中带版本的成果表；
- 影像和矢量瓦片；
- 路网图、空间索引或机器学习模型；
- 可供服务读取的对象存储目录；
- 供后续任务继续加工的中间数据集。

发布时还要考虑新旧版本切换。在线请求不应该在成果只生成一半时读到它，也不应该在切换后继续长时间引用旧缓存。

## 在线请求链路真正负责什么

在线链路的约束来自一个事实：请求发出后，有消费者正在等待。

### 1. 请求进入与边界校验

用户提交的范围、坐标系、过滤条件和输出格式都可能影响计算量。

请求入口需要检查：

- 身份和数据权限；
- 参数类型与业务合法性；
- 坐标范围和空间参考；
- 查询面积、时间范围和最大返回量；
- 是否允许执行高成本分析；
- 是否可以复用已有结果。

如果一个接口允许用户提交任意大小的多边形并返回所有相交要素，它实际上把系统资源的控制权交给了请求方。

### 2. 给每一步分配延迟预算

在线请求不能只设置一个总超时，然后让内部步骤自由消耗时间。

一条请求的时间可能分给：

```text
接入与鉴权
→ 缓存查询
→ 数据库检索
→ 空间计算
→ 结果序列化
→ 网络传输
→ 客户端解析与渲染
```

数据库查询节省的 100 毫秒，可能被超大的 GeoJSON 序列化和传输重新消耗。服务端很快返回，也不代表用户很快看到画面。

因此，在线性能必须沿完整请求链路观察，而不是只盯着某一条 SQL。

### 3. 用索引缩小实时计算范围

在线空间查询的关键通常不是让精确计算本身变快，而是先减少参与精确计算的数据量。

PostGIS 的空间索引可以通过边界框或索引感知的空间函数完成预筛选，再对候选几何执行精确关系判断。这个过程非常适合在线链路：把全表计算缩小为与当前请求范围相关的一小批对象。

但索引不是万能答案。坐标系不一致、返回字段过多、几何过于复杂、查询范围没有限制，仍然可能让请求变慢。

### 4. 缓存重复结果

在线请求并不意味着每次都必须重新计算。

如果请求能够形成稳定的缓存键，结果也允许在一定时间内复用，就可以把一次在线计算变成后续请求的已生产成果。

缓存需要回答：

- 哪些请求参数属于缓存键；
- 结果在多长时间内有效；
- 数据更新后怎样失效；
- 不同用户权限能否共享；
- 是否允许返回稍旧的结果；
- 缓存未命中时由谁承担首次计算成本。

HTTP 缓存能够通过新鲜度、验证器和缓存指令复用已有响应，但缓存的正确性不只是技术配置。它最终取决于业务是否允许复用，以及缓存键是否完整表达了请求差异。

### 5. 超时、限流与降级

离线任务失败后可以等待重试，在线请求却不能无限占用连接和计算资源。

常见策略包括：

- 限制请求范围和返回数量；
- 为高成本接口设置并发上限；
- 超过同步时限后转为异步任务；
- 返回较低精度或较旧但可用的成果；
- 在依赖服务不可用时快速失败；
- 记录慢请求和各阶段耗时。

OGC API Processes 同时支持同步执行和异步作业：当计算无法在一次请求中合理完成时，可以创建 job，让客户端查询状态并在完成后获取结果。它说明“由请求触发”不等于“必须让 HTTP 连接一直等待到计算结束”。

## 两条链路的性能目标为什么不同

假设有一亿条道路和历史积水记录需要生成风险统计。

离线任务可能用一小时完成，只要结果可靠、资源使用合理、失败可恢复，就是可以接受的。此时更重要的是：

- 每分钟处理多少数据；
- 并行后能否缩短总耗时；
- 中间成果是否可以复用；
- 失败重试会不会重复写入；
- 结果是否完整并通过质量检查。

如果同样的计算被放进在线接口，用户不会接受等待一小时。系统必须减少数据范围、提前生产基础成果、限制请求条件，或者把任务改为异步执行。此时更重要的是：

- 请求的 P50、P95 和 P99 延迟；
- 峰值时每秒能处理多少请求；
- 缓存命中率；
- 超时和错误比例；
- 单个慢请求是否影响其他用户；
- 服务降级后是否仍然可用。

平均延迟可能掩盖问题。十次请求中九次很快、一次需要十秒，平均值看起来未必夸张，但那一次长尾延迟会直接影响用户体验，也可能持续占用线程、连接和数据库资源。

所以：

```text
离线链路关心完成整批工作的总成本；
在线链路关心每个请求在资源竞争下的响应边界。
```

## 同一个 GIS 操作既可以离线，也可以在线

不能根据工具或算法名称判断它属于哪条链路。

| GIS 操作 | 离线使用 | 在线使用 |
| --- | --- | --- |
| 坐标转换 | 批量统一整个数据集 | 转换当前请求提交的几何 |
| 地图切片 | 提前生成静态瓦片 | 首次请求时动态生成并缓存 |
| 缓冲区 | 生产标准保护区成果 | 根据用户输入半径即时计算 |
| 路径规划 | 提前构建路网图和代价 | 根据起终点实时搜索路径 |
| 淹没分析 | 预计算多个水位情景 | 根据当前水位启动即时或异步计算 |
| 影像渲染 | 批量生成预览和瓦片 | 根据范围、时间和样式即时出图 |
| 点云处理 | 降采样、分块并建立 LOD | 加载当前视野节点并执行轻量查询 |

真正的判断标准是：

1. 它由什么触发？
2. 执行时是否有人正在等待？
3. 结果是否持久化并被重复消费？
4. 失败后是重试任务，还是向请求方返回错误？
5. 优化目标是整批吞吐量，还是单次请求延迟？

同一个 `ST_Intersects`，在夜间批量更新风险表时属于离线生产；在用户框选范围后即时查询时属于在线请求。

## 真实 GIS 系统通常是混合链路

如果所有内容都离线计算，系统缺乏灵活性和时效性；如果所有内容都在请求时计算，延迟和资源成本又难以控制。

更常见的做法是：

> 把稳定、昂贵、可复用的工作提前，把个性化、时效性强、计算范围较小的工作留在请求阶段。

### 在线地图：提前生成一部分瓦片，按需补齐其余内容

```text
离线：数据清洗 → 样式确定 → 常用范围和层级预生成瓦片
在线：请求瓦片 → 缓存命中直接返回
                  → 未命中时生成并写入缓存
客户端：加载瓦片 → GPU 渲染 → 地图交互
```

GeoWebCache 同时支持请求到来时生成瓦片和提前 seeding。提前生成能减少用户首次等待，但消耗生产时间和磁盘；按需生成只缓存真正访问过的区域，却会让第一次请求承担生成成本。官方文档给出的实践也是组合两种方式：常用范围和层级提前生成，低概率访问内容按需补齐。

这正是离线与在线边界可以动态移动的例子。

### 路径规划：离线建图，在线搜索

```text
离线：道路清洗 → 拓扑构建 → 转向规则 → 代价预处理
在线：起终点匹配 → 图搜索 → 动态约束 → 返回路线
```

如果请求到来后才从原始道路文件重新构建拓扑，绝大部分时间会浪费在所有请求都能复用的基础工作上。

### 灾害分析：离线准备底座，在线组合当前状态

```text
离线：DEM、建筑和道路治理 → 空间索引 → 多个标准情景
准实时：气象、水位和传感器状态更新
在线：选择当前情景 → 查询影响对象 → 返回结果
```

对于无法快速完成的精细模拟，可以由在线请求创建异步任务，而不是阻塞同步接口。

### 移动端：离线数据包与本地即时请求并存

```text
离线生产：地图切片 → 索引 → 压缩 → 生成终端数据包
本地请求：用户点击或框选 → 查询本地索引 → 返回结果 → 渲染
```

这里没有互联网连接，仍然同时存在提前生产和请求时计算两条链路。这再次说明“离线/在线”描述的是运行时机，而不是部署地点。

## 怎样决定一个计算应该放在哪里

可以先问九个问题：

1. 结果是否会被大量请求重复使用？
2. 输入范围和参数能否提前确定？
3. 数据变化频率有多高？
4. 计算能否稳定地在请求时限内完成？
5. 用户是否必须获得最新结果？
6. 结果是否需要审计、归档和复现？
7. 在线峰值是否承受得住重复计算？
8. 业务是否允许返回稍旧但稳定的结果？
9. 能否拆成离线基础成果和在线轻量组合？

一个实用的判断方式是：

```text
稳定 + 昂贵 + 可复用
→ 尽量提前离线生产

个性化 + 时效性强 + 范围有限 + 计算较轻
→ 适合在线请求时执行

昂贵 + 要求较新 + 无法完全预知参数
→ 预计算基础成果 + 增量更新 + 在线组合或异步任务
```

把计算提前，本质上是在用存储和数据新鲜度换请求时间；把计算推迟到请求阶段，则是在用实时计算资源换灵活性和最新状态。

系统设计的难点，就是找到业务能够接受的交换点。

## 两条链路如何定位故障

离线和在线链路表面上会共享数据库和算法，但故障形态不同。

### 离线链路常见问题

- 某个数据分区没有处理；
- 同一批次重复执行并产生重复成果；
- 输入数据在任务过程中发生变化；
- 中间结果损坏，却被后续步骤继续使用；
- 新版本只发布了一部分；
- 结果生成成功，但质量指标异常；
- 任务失败后无法从断点恢复。

排查时要沿“批次—输入版本—处理阶段—输出版本—发布状态”追踪。

### 在线链路常见问题

- 请求参数导致查询范围失控；
- 空间索引没有被使用；
- 缓存键遗漏参数或权限维度；
- 数据库查询很快，但序列化和传输很慢；
- 单个复杂请求占满工作线程；
- 依赖服务超时并层层放大；
- 服务返回成功，客户端却无法及时渲染大量结果。

排查时要沿“接入—缓存—查询—计算—序列化—传输—消费”记录各阶段耗时。

### 混合链路特有的问题

混合系统还要检查：

- 在线服务是否读取了正确的离线成果版本；
- 新旧成果切换是否完整；
- 数据更新后缓存是否正确失效；
- 在线参数与离线生产规则是否一致；
- 增量更新是否遗漏了相关对象；
- 旧版本是否仍被某些终端或节点长期引用。

很多所谓“在线查询错误”，真正原因是离线成果没有更新；很多所谓“数据生产错误”，也可能只是在线缓存仍然返回旧版本。

## 回到 GIS 全链路

现在可以给两条链路一个更准确的定义：

> 离线处理链路把不确定、庞大和昂贵的数据工作，提前转换为可复用、可验证、可发布的稳定成果。

> 在线请求链路在有限的延迟和资源预算内，根据当前请求组合数据与能力，并把结果可靠地交付给消费者。

它们共享数据、处理、分析、服务和渲染等 GIS 责任，但运行目标不同：

```text
离线生产决定在线系统能够站在怎样的数据基础上；
在线请求决定这些基础能力怎样被当前用户真正使用。
```

真正成熟的系统不会简单选择其中一边，而会持续调整计算发生的位置：能稳定复用的向前移动，必须响应当前状态的留在请求阶段，耗时但又无法预先完成的转为异步任务。

理解这条边界后，下一篇就可以进入具体系统形态：**WebGIS 从空间数据服务到浏览器渲染的完整链路。**届时我们会看到，一个看似简单的地图请求，背后怎样同时消费离线生产的空间成果和在线运行的数据服务。
