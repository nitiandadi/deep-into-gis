# 拓扑与空间关系：GIS 如何描述相交、邻接、包含与连通

<p class="post-meta">2026-07-28 · GIS 核心概念 · 拓扑与空间关系 · 约 36 分钟</p>

前面几章讨论的是空间对象“在哪里”：坐标怎样表达位置，地球模型怎样为坐标提供基准，地图投影又怎样把曲面位置转换到平面。

这一章讨论一个更容易被图形掩盖的问题：

> 空间对象之间究竟是什么关系？

先看一组外观几乎相同的道路。

```text
场景一：两条道路在普通十字路口相交，车辆可以转向
场景二：高架从地面道路上方穿过，两条道路并不连通
场景三：两条道路存在交叉节点，但交通规则禁止某些转向
```

如果只看二维线条，它们都可能是一个“十字”。但对 GIS 来说，三个场景拥有完全不同的关系：

```text
二维几何关系：线条是否相交
网络拓扑关系：是否存在公共节点
业务语义关系：是否允许从一条路进入另一条路
动态状态关系：当前时刻是否可以通行
```

坐标和几何能够画出道路，却不能独自回答这些问题。拓扑存在的意义，就是把那些容易被形状和坐标掩盖的关系，变成可以表达、检查和计算的结构。

## 拓扑为什么会被提出来

### 传统几何擅长度量，却不擅长纯粹的连接问题

传统几何主要研究长度、角度、面积、比例和具体形状。但有些问题看起来属于几何，答案却与这些量完全无关：

- 一组岛屿和桥梁能否一次走遍；
- 一条闭合曲线是否把平面分成内部和外部；
- 两个区域是否相邻；
- 一个网络是否连通；
- 一个表面有几个孔洞；
- 对象连续变形后，哪些性质仍然不变。

这些问题需要的不是更精确的尺子，而是一种专门研究位置、连接、边界和连续性的语言。

莱布尼茨曾设想一种“位置的几何”——`geometria situs`。它要表达的不是量有多大，而是对象怎样相互排列和连接。这个想法后来逐渐发展成拓扑学。

### 1736 年：欧拉把一座城市压缩成节点和边

柯尼斯堡城被河流分成四块陆地，七座桥把它们连接起来。当时的问题是：

> 能否选择一条路线，使七座桥每座恰好经过一次？

地图上有桥梁长度、河流弯曲、陆地形状和相互距离，但欧拉发现这些信息都不影响答案。他只保留两类对象：

```text
陆地区域 → 节点
桥梁     → 边
```

城市地图于是变成一个抽象网络。问题也从“在地图上怎样走”变成“这个节点—边结构是否存在满足条件的路径”。

欧拉并没有建立今天完整的拓扑学，但这次抽象清楚展示了一个重要思想：

> 某些空间问题只与连接结构有关，与对象的大小、距离和具体形状无关。

欧拉的论文题目《与位置几何有关的问题的解答》也直接指出，这类问题不适合用普通的数量计算解决。

从现代 GIS 回看，七桥问题的结构仍然随处可见：

```text
七桥问题：能否沿所有桥通过一次
道路导航：从起点到终点是否存在路径
管网分析：水流能否到达某个用户
河网分析：污染物会流经哪些河段
自动驾驶：车辆能否沿车道连接到达目标位置
```

### 19 世纪：拓扑开始成为独立概念

1847—1848 年，Johann Benedict Listing 在《Vorstudien zur Topologie》中系统使用 `Topologie` 一词。他关注的是点、线、面和体之间的连接、次序和相互位置，并把这些问题与度量和大小区分开。

到了 1895 年，庞加莱发表《Analysis Situs》，开始系统研究连通性、孔洞、边界以及不同空间之间的连续变形关系，并使用代数方法寻找能够区分空间结构的不变量。

这里不需要进入基本群、同调等纯数学内容。对 GIS 最重要的是一个思想：

> 可以忽略对象大量具体形状，只保留决定其空间结构的关系。

一块地无论整体平移、旋转、缩放，还是把边界画得更平滑，只要没有撕裂、粘合或穿孔，它与周围地块的邻接关系、内部和外部仍然可以保持不变。

## 从数学拓扑到数字地图

### 纸质地图只要能看，数字地图还必须能算

在纸质地图中，人可以直接看出两条道路是否连接、两个地块是否相邻、湖泊中是否有岛。计算机却只看到一串坐标：

```text
LineString A = [(x1, y1), (x2, y2), ...]
LineString B = [(u1, v1), (u2, v2), ...]
```

仅仅把纸图数字化成点和线，会立即出现一批新问题：

- 两条线看起来接上了，坐标是否真正相同？
- 道路交叉处是否应该建立节点？
- 一条边左右分别属于哪个地块？
- 两个地块共享的边界为什么要保存两遍？
- 修改共享边界时，怎样保证两侧一起变化？
- 怎样自动发现缝隙、重叠、悬挂线和错误连接？
- 怎样从线条恢复出完整的面？

地图从“图形”变成“数据”以后，空间关系必须被显式表达或可靠计算。

### 1967 年：DIME 开始编码街道和街区关系

美国人口普查局在 1967 年测试中开发 DIME，用于存储街道、节点、街区、地址范围及其关系。

它的价值不只是把道路坐标放进计算机，而是记录类似下面的信息：

```text
道路段从哪个节点开始
道路段到哪个节点结束
道路段左侧属于哪个街区
道路段右侧属于哪个街区
```

这类结构后来成为数字道路网络、人口普查地理和 GIS 拓扑的重要基础。

### 1970—1980 年代：节点—边—面模型成为经典 GIS 结构

随着 Harvard Laboratory 的 POLYVRT、ODYSSEY，以及后来 Arc/Info Coverage 等系统发展，矢量 GIS 逐渐形成经典的拓扑结构：

```text
Node
├─ 线的端点和交叉点

Edge / Arc
├─ 保存有方向的坐标序列
├─ 引用起点和终点
├─ 记录左侧面和右侧面

Face / Polygon
└─ 由一组有方向的边围成
```

它集中解决了三类问题：

- **关联（Incidence）**：哪个节点位于哪条边上；
- **邻接（Adjacency）**：哪些面共享同一条边；
- **连通（Connectivity）**：能否沿节点和边从一处到达另一处。

GIS 在这一阶段把拓扑当作需要显式保存和维护的数据结构。

### 1990 年代：拓扑又成为统一的空间关系语言

显式拓扑模型很强，但结构复杂，而且不同系统的内部实现并不一致。很多空间查询其实只想知道：

```text
点是否在行政区内？
两个地块是否接触？
道路是否穿过规划区？
两个面是重叠，还是一个包含另一个？
```

这推动 GIS 研究者寻找一种不依赖具体存储结构的形式模型。

1991 年，Egenhofer 与 Franzosa 从点集拓扑出发，用对象内部和边界之间的交集定义空间关系；Egenhofer 与 Herring 随后把外部加入模型，形成九交框架。1993 年，Clementini、Di Felice 与 van Oosterom 进一步用交集维度增强表达能力，逐渐形成今天常用的 DE-9IM。

1999 年前后的 OGC Simple Features 进一步统一了 Point、LineString、Polygon 等几何类型，以及 `Intersects`、`Contains`、`Touches`、`Crosses`、`Relate` 等空间谓词。

从此，GIS 拓扑形成两条并行路线：

```text
显式拓扑
把节点、边、面和共享关系存进数据结构

关系拓扑
根据几何计算内部、边界和外部之间的关系
```

今天的 JTS、GEOS、PostGIS 等几何引擎主要实现第二条路线；PostGIS Topology、传统 Coverage、地籍和网络数据模型仍会使用第一条路线。二者有关联，但不能混为一谈。

## 拓扑的本质是什么

数学上，拓扑关心的是在连续变形下保持不变的性质。可以把对象拉伸、压缩或弯曲，但不能撕开、粘合或凭空打洞。

对 GIS 来说，最有用的拓扑不变量包括：

- 是否连通；
- 是否相离；
- 是否包含；
- 是否接触；
- 是否共享边界；
- 一个对象位于另一个对象内部还是外部；
- 一条线是否形成闭环；
- 一个面包含几个孔洞；
- 一个网络有几个连通分量。

这里需要同时区分几种经常被统称为“空间关系”的概念。

| 关系类型 | 典型问题 | 是否属于拓扑核心 |
|---|---|---|
| 拓扑关系 | 相离、接触、包含、重叠、连通 | 是 |
| 度量关系 | 距离多远、面积多大、长度多少 | 否 |
| 方向关系 | 位于东侧、左侧、上游还是下游 | 不完全是 |
| 网络关系 | 是否有路径、是否可达 | 属于图拓扑 |
| 业务关系 | 是否允许转向、属于哪个管理对象 | 需要拓扑支撑，但还包含语义 |
| 时态关系 | 当前是否开放、关系何时有效 | 是拓扑的动态扩展 |

所以，“拓扑与空间关系”不是说所有空间关系都是拓扑关系，而是用拓扑建立其中最基础、最稳定的一层。

::: tip GIS 中“拓扑”的两个核心含义
它既指相交、邻接、包含、连通等关系，也指显式组织节点、边、面及共享关系的数据模型。
:::

## 从维度理解点、线和面

在 GIS 中：

- 点是零维对象；
- 线是一维对象；
- 面是二维对象。

交集也有维度：

```text
两条线交于一个点       → 交集维度为 0
两条线重合一段         → 交集维度为 1
两个面共享一段边界     → 边界交集维度为 1
两个面只碰到一个角点   → 边界交集维度为 0
两个面重叠一块区域     → 内部交集维度为 2
```

“是否相交”只能给出一个布尔值，交集维度则能进一步解释相交发生在点、线还是面上。这正是 DE-9IM 中 `0、1、2` 的来源。

## 内部、边界和外部

OGC Simple Features 使用点集拓扑描述几何关系。任意几何对象都可以放到三个集合中观察：

- **内部（Interior，I）**：对象的主体；
- **边界（Boundary，B）**：内部与外部之间的分界；
- **外部（Exterior，E）**：整个空间中不属于对象的部分。

不同几何类型的内部和边界并不相同：

| 几何类型 | 内部 | 边界 | 外部 |
|---|---|---|---|
| Point | 点本身 | 空集 | 除该点外的空间 |
| LineString | 通常是去掉端点后的线 | 通常是两个端点 | 不在线上的空间 |
| Polygon | 外环以内且排除孔洞和边界的区域 | 外环和所有内环 | 面外以及孔洞内部 |

几个容易误解的地方：

- 点落在 Polygon 的洞中时，它位于 Polygon 的外部；
- 点落在 Polygon 边界上时，它不属于 Polygon 内部；
- 线的边界通常是端点，而不是整条线；
- 闭合 LineString 在常见的 mod-2 边界规则下可以没有边界；
- Polygon 的内环是边界，内环包围的孔洞是外部。

这些定义不是纯理论细节，它们会直接改变 `Contains`、`Covers`、`Touches` 等 API 的结果。

## DE-9IM：怎样把拓扑关系写成矩阵

设两个几何对象为 A 和 B。分别取两者的内部、边界和外部，再两两求交：

| A \ B | B 的内部 I(B) | B 的边界 B(B) | B 的外部 E(B) |
|---|---:|---:|---:|
| **A 的内部 I(A)** | I(A) ∩ I(B) | I(A) ∩ B(B) | I(A) ∩ E(B) |
| **A 的边界 B(A)** | B(A) ∩ I(B) | B(A) ∩ B(B) | B(A) ∩ E(B) |
| **A 的外部 E(A)** | E(A) ∩ I(B) | E(A) ∩ B(B) | E(A) ∩ E(B) |

九个交集组成九交模型。DE-9IM 中的 `D` 和 `E` 表示“维度扩展”：每个格子不仅记录是否为空，还记录非空交集的最高维度。

| 字符 | 含义 |
|---|---|
| `F` | 空集，维度为 -1 |
| `0` | 交集最高维度为零维 |
| `1` | 交集最高维度为一维 |
| `2` | 交集最高维度为二维 |
| `T` | 非空，具体维度不关心 |
| `*` | 任意结果 |

程序通常按行把矩阵展开为九个字符：

```text
II  IB  IE  BI  BB  BE  EI  EB  EE
```

### 点严格位于多边形内部

设 A 是点，B 是多边形：

```text
0FFFFF212
```

它满足 `Within` 模式：

```text
T*F**F***
```

反过来，多边形对点满足 `Contains`。

### 点位于多边形边界

点的内部不再与多边形内部相交，而是与多边形边界相交：

```text
F0FFFF212
```

此时通常有：

```text
point.within(polygon)    = false
polygon.contains(point) = false
polygon.covers(point)   = true
point.touches(polygon)  = true
```

`Contains` 和 `Covers` 的差异不是软件随意设计出来的，而是二者对边界的要求不同。

### 两条线在中段交叉

一条水平线和一条竖直线在各自中段相交，交集是一个点：

```text
0F1FF0102
```

两条线满足 `Crosses`，而不是 `Touches`。原因是它们的内部在零维点上相交，并且双方都有部分继续延伸到对方外部。

### 两个面共享边线和只碰角点

两个地块只在角点接触，以及共享一段边界，都可能满足 `Touches`。如果业务要求“相邻地块必须共享边线”，就要继续检查边界交集维度：

```text
F***1****  → 边界交集为一维，共享一段边线
F***0****  → 边界交集为零维，只共享角点
```

这说明具名谓词是对九交矩阵的常用封装，完整矩阵则能表达更精确的业务条件。

## 常见空间谓词到底在说什么

| 谓词 | 核心语义 |
|---|---|
| `Disjoint` | 内部和边界完全没有交集 |
| `Intersects` | `Disjoint` 的反面，存在任意形式的相交 |
| `Within` | A 位于 B 内部范围中，且没有部分位于 B 外部 |
| `Contains` | A 包含 B，是 `Within` 的逆关系 |
| `Covers` | B 没有任何部分位于 A 外部，允许只落在边界上 |
| `Touches` | 双方内部不相交，但至少一方的内部或边界与对方边界接触 |
| `Crosses` | 对象内部发生较低维的穿越式相交 |
| `Overlaps` | 同维对象部分重叠，双方都有不属于对方的部分 |
| `EqualsTopo` | 两个几何表达相同的点集 |

### `Intersects` 不等于 `Overlaps`

`Intersects` 的范围非常宽：

- 端点接触；
- 共享边界；
- 一条线穿过一个面；
- 一个面包含另一个面；
- 两个面部分重叠。

这些都属于相交。

`Overlaps` 更严格。它通常要求对象维度相同、内部有同维交集，并且双方都有一部分不属于对方。一个面完全包含另一个面，不叫 `Overlaps`。

### `Contains` 不一定符合业务中的“包含”

行政区边界上的点应该属于哪个区，不是拓扑模型能够替业务决定的。

- 使用 `Contains`：边界点可能不命中任何区；
- 使用 `Covers`：相邻两个区可能同时命中边界点；
- 使用人为归属规则：可以保证结果唯一，但它属于业务语义。

拓扑提供精确定义，业务仍要选择符合自身规则的谓词。

## DE-9IM 真正统一了什么

如果没有统一模型，空间关系很容易被实现成一组彼此独立的几何算法：

```text
Touches  写一套端点和边界判断
Contains 写一套点在面内和线面判断
Overlaps 再写一套重叠判断
Crosses  又写一套穿越判断
```

问题不只是代码重复。点—线、点—面、线—线、线—面、面—面拥有不同的维度组合，每个谓词还要处理端点、孔洞、多部件几何和边界规则。若每个关系各自定义：

- 很难证明谓词是否完整；
- 不同谓词可能给出互相矛盾的结果；
- 不同软件可能对同一个名称采用不同语义；
- 增加一个自定义关系就要重新进入底层几何算法；
- 修复精度和鲁棒性问题时，需要修改多套实现。

DE-9IM 把问题拆成了两层。

### 第一层：统一计算拓扑事实

底层几何引擎集中回答一个统一问题：

> A、B 的内部、边界和外部如何相交？

更具体地说，就是确定九个交集是否为空，以及非空交集的最高维度：

```text
dim(I(A) ∩ I(B))   dim(I(A) ∩ B(B))   dim(I(A) ∩ E(B))
dim(B(A) ∩ I(B))   dim(B(A) ∩ B(B))   dim(B(A) ∩ E(B))
dim(E(A) ∩ I(B))   dim(E(A) ∩ B(B))   dim(E(A) ∩ E(B))
```

为了得到这些事实，底层仍然要处理复杂的计算几何问题：

- 线段是否相交以及交点在哪里；
- 点落在线内部、端点还是线外；
- 点位于面的内部、边界、孔洞还是外部；
- 两组边界交于点、线还是面；
- 交叉位置怎样进行节点化；
- 多部件几何和闭合线采用什么边界规则；
- 浮点精度下怎样保持计算鲁棒性。

DE-9IM 没有消灭复杂几何算法，而是把它们收敛到一个统一的“拓扑事实生产层”。

### 第二层：用规则解释拓扑事实

矩阵得到以后，上层不再重新研究坐标，而是匹配规则：

```text
统一计算拓扑事实
        ↓
DE-9IM Intersection Matrix
        ↓
不同规则解释这些事实
        ↓
Touches / Crosses / Overlaps
Contains / Within
Equals / Covers / CoveredBy
```

其中一些关系可以用一个模式表示：

| 关系 | 典型 DE-9IM 模式 |
|---|---|
| `Disjoint` | `FF*FF****` |
| `Within` | `T*F**F***` |
| `Contains` | `T*****FF*` |
| `EqualsTopo` | `T*F**FFF*` |

`Touches`、`Crosses`、`Overlaps` 会根据输入几何维度使用不同模式；`Covers` 和 `CoveredBy` 也可以匹配多种允许边界参与的模式。上层谓词的本质仍然一致：

```text
predicate(A, B)
=
match(relate(A, B), predicateRules, dimensionA, dimensionB)
```

例如，底层只要确定“点的内部与 Polygon 边界交于零维点，点的内部与 Polygon 内部不相交”，上层就能同时推出：

```text
Touches   = true
Within    = false
CoveredBy = true
```

不需要分别实现三套点—面算法。

### 自定义关系也变成了规则

假设地籍业务中的“相邻地块”必须共享一段边线，仅碰到角点不算相邻。底层仍然计算同一份九交事实，上层只增加一个模式：

```text
F***1****
```

它表达：

- 两个面的内部不相交；
- 两个面的边界交集是一维；
- 其他格子不影响当前规则。

这使 DE-9IM 不只是标准谓词的实现基础，也成为自定义空间关系的规则语言。

::: tip DE-9IM 的核心架构价值
它把“怎样可靠计算几何交集”和“业务把什么称为接触、穿越、包含或邻接”分开。底层负责事实，上层负责语义。
:::

### 统一语义不代表每次都完整计算矩阵

从概念上看，所有谓词都可以通过完整 DE-9IM 矩阵解释；从工程实现看，高性能几何库不一定每次都把九个格子全部算完。

例如判断 `Intersects` 时，只要发现任意一个有效公共点，结果就已经确定；判断某些包含关系时，包围盒和维度也可以提前排除不可能情况。继续计算剩余交集只会浪费时间。

因此 JTS、GEOS 等库可以采用：

- 包围盒预判；
- 按谓词需要计算部分拓扑事实；
- 结果一旦确定就短路返回；
- 对重复查询的固定几何建立 Prepared 空间索引；
- 只有调用 `relate()` 时才生成完整矩阵。

优化改变的是“需要计算多少事实”，不改变谓词最终遵循的 DE-9IM 语义。

## DE-9IM 不等于完整的 GIS 拓扑

DE-9IM 能回答：

- 点是否位于面内部；
- 两个面是否接触或重叠；
- 线是否穿过面；
- 两条线是否在二维平面相交；
- 两个几何是否表示相同点集。

它不能独自回答：

- 两条相交道路是否在路网中连通；
- 管线交叉处是否安装了三通；
- 两条道路是否位于不同高度；
- 车辆是否允许转向；
- 阀门关闭后水流能否通过；
- 某条连接在施工期间是否有效。

原因在于 DE-9IM 观察的是几何点集。对象标识、方向、层级、规则、参与者和时间并不属于二维点集本身。

## 简单要素模型：独立保存几何，按需计算关系

Shapefile、GeoJSON 和普通空间数据库表通常使用简单要素思路。每个 Feature 独立保存自己的完整几何。

假设地块 A 和地块 B 相邻：

```text
地块 A 保存一份公共边界坐标
地块 B 再保存一份公共边界坐标
```

即使两份坐标最初完全一致，分别编辑后也可能产生：

- 很窄的缝隙；
- 很小的重叠；
- 两条不完全重合的边；
- 难以解释的碎面。

简单要素的优势是：

- 模型简单；
- 要素可以独立读取和交换；
- 适合通用空间查询；
- 容易进入 GeoJSON、WKB、数据库和 Web API；
- 不要求所有数据先构建统一拓扑。

其代价是：共享关系通常没有永久保存，需要运行时计算，也不会自动保证长期一致。

调用一次 `polygonA.touches(polygonB)`，只能判断当前坐标是否满足接触关系，不能保证未来编辑后它们仍然接触。

## 显式拓扑模型：共享节点、边和面

显式拓扑把坐标和空间对象之间增加了一层拓扑基础元素：

```text
Node：零维节点
Edge：有方向的边
Face：由边围成的面
```

一条 Edge 通常记录：

```text
start_node
end_node
edge_geometry
left_face
right_face
```

两个相邻地块不再各自保存一份公共边界，而是共同引用同一条 Edge，只是使用方向可能相反。

```text
地块 A ──引用──┐
               ├── 公共 Edge
地块 B ──引用──┘
```

这样做带来几个重要结果：

- 修改共享边时，两侧地块会一起变化；
- 相邻关系可以由左右面直接获得；
- 面可以通过一组有向边重建；
- 网络连通关系可以通过节点引用获得；
- 重复边界和不一致编辑显著减少。

显式拓扑的代价同样明显：

- 数据结构更复杂；
- 编辑一条边可能影响多个要素；
- 构建和维护需要容差与严格规则；
- 跨系统交换比独立几何困难；
- 不适合所有临时分析和轻量应用。

因此，现代 GIS 并没有在简单要素和显式拓扑之间选择唯一胜者，而是根据任务决定。

| 需求 | 更常见的选择 |
|---|---|
| 通用数据交换和 Web API | 简单要素 |
| 临时空间查询和叠加 | 简单要素＋按需谓词 |
| 地籍共享边界长期维护 | 显式拓扑 |
| 行政区无缝覆盖 | 显式拓扑或严格拓扑规则 |
| 道路、管网和河网连通 | 图或网络拓扑 |
| 数据库内管理 Node、Edge、Face | PostGIS Topology 等模型 |

## 拓扑规则是在表达业务约束

拓扑模型不会自动知道什么关系才算正确。同一种几何关系，在不同数据中可能有不同含义。

### 地籍和土地覆盖

常见规则：

- 地块不能重叠；
- 地块之间不能出现非预期缝隙；
- 相邻地块应共享一致边界；
- 地块必须位于指定行政范围内。

### 行政区划

常见规则：

- 同级行政区不能重叠；
- 下级行政区必须位于上级行政区内部；
- 相邻行政区边界应该一致；
- 行政区集合应形成完整覆盖。

### 道路网络

常见规则：

- 路段端点必须落在合法节点上；
- 平交路口需要建立连接；
- 高架和地面道路不能因二维交叉而错误连接；
- 不应存在非预期悬挂路段；
- 道路方向和转向关系必须一致。

### 管网

常见规则：

- 管线端点必须连接节点、阀门或设备；
- 交叉但不连通的管线不能自动建立连接；
- 设备必须挂接到正确管段；
- 网络方向和设施状态需要参与追踪。

所以，拓扑规则不是“所有线必须连接”之类的统一命令。死胡同道路允许悬挂，孤立设备也可能是合法对象。错误与否取决于数据模型和业务语义。

## 常见拓扑错误是怎样产生的

| 错误 | 表现 | 可能影响 |
|---|---|---|
| 欠冲 | 线没有延伸到应该连接的位置 | 路网或管网断开 |
| 过冲 | 线穿过目标节点继续延伸 | 产生错误悬挂段 |
| 悬挂 | 端点没有连接其他对象 | 可达性和追踪中断 |
| 伪节点 | 本可连续的线被无意义切分 | 网络碎片化、维护困难 |
| 重复线 | 同一位置保存多条相同线 | 重复统计和错误连接 |
| 面缝隙 | 应无缝覆盖的面之间存在空隙 | 面积缺失、查询漏选 |
| 面重叠 | 本应互斥的面覆盖同一区域 | 归属冲突、面积重复 |
| 碎面 | 叠加或精度误差产生狭小多边形 | 统计噪声和数据膨胀 |
| 自相交 | 单个面边界穿过自身 | 几何无效、叠加失败 |
| 错误结点化 | 高架与地面道路被切成公共节点 | 路由穿越不存在的路口 |

需要区分两类问题：

```text
几何有效性错误
→ 单个 Geometry 本身不合法，例如 Polygon 自相交

拓扑规则错误
→ 多个合法 Geometry 之间的关系不符合业务要求
```

两个 Polygon 可以各自都合法，却发生不应存在的重叠；一条合法 LineString 也可能没有连接到应连接的管网节点。

## 理论上与坐标无关，计算时为什么仍会出错

拓扑理论研究的是不依赖具体坐标值的关系，但计算机必须通过有限精度坐标判断这些关系。

现实数据中经常出现：

```text
道路端点 A = (100.0000, 200.0000)
道路端点 B = (100.0001, 200.0000)
```

业务上它们可能表示同一个路口，数学上却是两个不同点。

### 容差和吸附

GIS 常使用容差或吸附，把足够接近的顶点归并到一起。但容差不是越大越好：

- 过小：应该连接的对象仍然断开；
- 过大：原本相离的对象被错误连接；
- 单位错误：把“米”的容差用于“度”坐标；
- 数据精度不一致：高精数据被低精数据拉偏；
- 不分层处理：高架和地面道路被吸附到同一节点。

吸附本身会改变拓扑。它不是单纯的数值清理，而是在做“哪些点应该被视为同一点”的业务决定。

### 鲁棒性和精度模型

线段求交、面叠加和节点化需要大量方向判断与交点计算。浮点误差可能造成：

- 理论交点没有被识别；
- 交点落在输入线段范围外；
- 叠加产生极小碎片；
- 几何引擎抛出 `TopologyException`；
- 不同软件得到略有差异的结果。

工程中需要结合：

- 合适的投影坐标和单位；
- 明确的数据精度；
- 精度网格或 Precision Model；
- 鲁棒几何算法；
- 结果有效性检查；
- 业务控制点和人工抽检。

::: warning 不要把“拓扑修复”理解成一键清理
自动吸附、简化和修复可能消除错误，也可能改变边界、面积、连接和权属。修复结果必须回到数据精度与业务规则中验证。
:::

## 应用一：地籍、行政区与共享边界

地籍是显式面拓扑最典型的场景。

两个相邻地块之间的界址线不是两条“看起来差不多”的线，而应是同一条法律或测量边界。若两侧分别维护坐标，可能出现：

```text
地块 A 认为边界在 x = 100.00
地块 B 认为边界在 x = 100.03
```

三厘米差异在小比例尺地图上看不出来，却可能造成权属、面积和工程放样问题。

通过共享 Edge，可以让两块地共同引用一份边界。修改边界时，两个地块同时更新，并保持：

- 无重叠；
- 无缝隙；
- 边界一致；
- 邻接关系明确。

行政区、土地利用和规划分区也有类似需求。拓扑不只是提升查询速度，更是在维护一张无缝空间覆盖的逻辑一致性。

## 应用二：空间查询与叠加分析

DE-9IM 最直接的应用是空间查询：

```text
哪些医院位于行政区内？
哪些道路穿过规划范围？
哪些地块与洪水淹没区相交？
哪些建筑接触保护区边界？
两个版本的用地范围是否仍然相等？
```

叠加分析同样依赖拓扑：

- Intersection；
- Union；
- Difference；
- SymDifference；
- Clip；
- Polygonize。

这些操作不只是计算新坐标，还要重新判断：

- 哪些交点成为节点；
- 哪些边属于结果；
- 哪些环形成面；
- 哪些区域是洞；
- 哪些碎片应该保留。

因此 Polygon Overlay 的困难并不主要在“求两条线的交点”，而在交点产生后怎样重建一致的拓扑结构。

## 应用三：道路与导航网络

道路导航通常把现实道路抽象成有向图：

```text
Node
+ Edge
+ Direction
+ Cost
+ Turn Restriction
= Routable Network
```

几何相交只产生候选关系，不能直接决定图连通。

二维中同样是十字交叉，可能代表：

1. 普通平交路口，需要切分道路并建立公共节点；
2. 高架跨越，不应建立连接；
3. 存在连接节点，但某些转向禁止；
4. 当前施工封闭，静态图可达但暂时不可通行。

所以道路系统通常显式保存：

- 起点和终点；
- 前驱和后继；
- 单向和双向；
- 道路层级；
- 转向限制；
- 通行成本；
- 有效时间。

路线规划消费的是这张图，而不是屏幕上道路是否“碰在一起”。

## 应用四：水务、燃气、电力与通信网络

管网中的空间距离和网络距离完全不同。两条管线可能相距几厘米却互不连通，也可能在地图上相隔很远但通过网络路径连接。

以爆管分析为例：

```text
确定爆管所在管段
→ 沿网络向上游和下游追踪
→ 经过三通、阀门和设备
→ 遇到关闭阀门停止
→ 找出受影响管段、设施和用户
```

这里至少存在三层关系：

```text
几何拓扑：管线和设备在空间中怎样相交
网络拓扑：节点和边怎样连接
运行拓扑：阀门、泵站和实时状态允许怎样流动
```

如果阀门关闭，几何和静态网络都没有变化，但当前可达关系已经改变。

这说明现代业务拓扑经常不是永久固定的图，而是：

```text
当前可用网络
= 静态网络
+ 设施状态
+ 方向与规则
+ 时间条件
```

## 应用五：河网、水文与栅格连通

河网可以表示成节点—边结构：

- 河源、汇流点和出口是节点；
- 河段是有方向的边；
- 高程和水流方向决定上下游；
- 汇流关系决定污染物或洪峰怎样传播。

栅格同样存在拓扑，只是表达方式不同。一个像元的邻居可以按规则定义：

```text
四邻域：上、下、左、右
八邻域：再加四个对角方向
```

选择四邻域还是八邻域，会直接改变：

- 连通区域数量；
- 岛屿和孔洞识别；
- Flood Fill 结果；
- 淹没区扩展；
- 图像分割；
- 栅格转矢量后的边界。

因此拓扑不只属于矢量点、线、面。凡是需要判断“谁与谁相邻、能否从这里传播到那里”的模型，都在处理某种连通结构。

## 应用六：自动驾驶中的车道拓扑

自动驾驶把道路网络进一步细化到车道级。

普通导航可能只需要知道“沿这条道路行驶，然后左转”。自动驾驶还要知道：

- 当前位于哪条车道；
- 下一条车道是谁；
- 左右是否存在相邻车道；
- 边线是否允许跨越；
- 哪些车道在路口形成冲突；
- 停止线和信号灯作用于哪条车道；
- 当前车辆类型是否允许进入；
- 当前状态是否满足通行条件。

可以把它分成五层：

| 层次 | 回答的问题 |
|---|---|
| 几何拓扑 | 车道面、边界、停止线怎样相交 |
| 网络拓扑 | 前驱、后继、合流、分流怎样连接 |
| 车道邻接 | 左右相邻以及是否允许换道 |
| 交通规则 | 限速、让行、信号灯和参与者限制 |
| 动态状态 | 施工、信号相位、事故和 ODD 是否允许通行 |

Lanelet2、OpenDRIVE、NDS 和厂商内部模型会以不同方式表达其中部分能力，但它们都没有脱离 GIS 的基础问题：

```text
对象在哪里
→ 几何上怎样相交
→ 网络上怎样连接
→ 规则上能否通行
→ 当前状态是否有效
```

DE-9IM 在自动驾驶中仍然有价值，例如：

- 检查左右边界是否交叉；
- 检查中心线是否位于车道面内；
- 检查停止线是否穿过目标车道；
- 发现车道面之间的异常缝隙和重叠；
- 生成潜在冲突候选。

但几何相交只是第一层。最终冲突关系还要结合高程、方向、规则和时间判断。

## 三维和时间为什么会改变拓扑结论

JTS、GEOS 和 OGC Simple Features 中最常见的谓词主要在 XY 平面计算。几何可以带 Z，但 Z 通常不参与 `Intersects`、`Touches` 等关系判断。

因此：

- 高架道路与地面道路在二维中相交；
- 不同楼层的房间投影到平面后可能重叠；
- 地下管线可能在 XY 上交叉却没有接口；
- 隧道和地面道路可能共享平面位置。

正确处理通常需要组合：

- 二维几何关系；
- 高程或楼层；
- 对象层级；
- 显式连接标识；
- 专用三维算法。

时间同样会改变关系：

- 潮汐车道改变方向；
- 道路施工导致连接失效；
- 阀门开关改变管网可达性；
- 行政边界按版本生效；
- 临时禁飞区改变可通行空间。

更完整的关系函数不是：

```text
connected(A, B)
```

而是：

```text
connected(A, B, participant, time, state, level)
```

这不是说传统拓扑失效了，而是现代系统在稳定的几何拓扑之上增加了条件和语义。

## JTS、GEOS、PostGIS 和拓扑模型分别处在哪一层

### JTS：事实矩阵、规则匹配和短路谓词

JTS 主要提供平面几何模型、DE-9IM 谓词、几何有效性检查和叠加运算。

`IntersectionMatrix` 是对 DE-9IM 的直接建模。JTS 可以先计算完整事实矩阵，再用标准或自定义规则解释：

```java
IntersectionMatrix matrix = a.relate(b);

System.out.println(matrix.toString());

boolean within             = matrix.isWithin();
boolean contains           = matrix.isContains();
boolean sharesBoundaryLine = matrix.matches("F***1****");
```

标准具名谓词向业务代码隐藏了矩阵细节：

```java
a.intersects(b);
a.touches(b);
a.crosses(b);
a.within(b);
a.contains(b);
a.covers(b);
a.overlaps(b);
a.equalsTopo(b);
```

它们在语义上由 DE-9IM 定义，但实现不必先生成完整九字符字符串。

JTS 1.20 的 `RelateNG` 更直接体现了“事实与谓词分离”的设计。它既可以返回完整 `IntersectionMatrix`，也可以接受具名谓词或自定义矩阵模式，并在结果已经确定时提前结束：

```java
IntersectionMatrix facts = RelateNG.relate(a, b);

boolean adjacent = RelateNG.relate(a, b, "F***1****");
boolean touches  = RelateNG.relate(
    a,
    b,
    RelatePredicate.touches()
);
```

如果要用同一个行政区反复判断大量点或要素，可以准备固定几何，缓存内部空间索引：

```java
RelateNG preparedArea = RelateNG.prepare(area);

for (Geometry candidate : candidates) {
    boolean covered = preparedArea.evaluate(
        candidate,
        RelatePredicate.covers()
    );
}
```

Prepared 模式没有改变 `Covers` 的定义，只是减少重复构建索引和重复扫描几何的成本。

### GEOS：把同一模型带到 C/C++ 与更多系统

GEOS 是 JTS 思想在 C/C++ 生态中的实现，也是 PostGIS、Shapely 等大量空间软件的重要几何基础。

GEOS C API 同样分成“返回事实矩阵”和“直接匹配规则”：

```c
char* matrix = GEOSRelate(a, b);

char adjacent = GEOSRelatePatternMatch(
    matrix,
    "F***1****"
);

GEOSFree(matrix);
```

不需要保留完整矩阵时，可以直接计算并匹配：

```c
char adjacent = GEOSRelatePattern(
    a,
    b,
    "F***1****"
);
```

GEOS 还提供 `GEOSTouches`、`GEOSCrosses`、`GEOSContains`、`GEOSWithin` 等具名谓词。它们向调用者暴露不同业务名称，底层仍共享统一的拓扑关系语义和几何计算能力。

对于一个固定几何与大量候选对象的重复关系判断，GEOS 也支持 Prepared Geometry 和 Prepared Relate Pattern，避免每次从头处理固定对象。

### PostGIS Geometry

普通 PostGIS `geometry` 主要使用简单要素模型。它把 GEOS 的几何能力暴露成 SQL，使“先取得事实、再解释规则”可以直接写进数据库：

```sql
SELECT ST_Intersects(a.geom, b.geom);
SELECT ST_Contains(a.geom, b.geom);
SELECT ST_Covers(a.geom, b.geom);

-- 返回完整 DE-9IM 事实矩阵
SELECT ST_Relate(a.geom, b.geom);

-- 直接判断自定义关系
SELECT ST_Relate(a.geom, b.geom, 'F***1****');
```

也可以先保存或取得矩阵，再单独匹配规则：

```sql
SELECT ST_RelateMatch(
    ST_Relate(a.geom, b.geom),
    'F***1****'
);
```

这些函数根据几何按需计算关系，并不要求数据预先存成共享 Node、Edge、Face。

在查询大量数据时，优先使用已有的 `ST_Intersects`、`ST_Contains` 等具名谓词，通常更容易利用空间索引和内部短路优化。只有标准谓词无法表达业务关系时，再使用 `ST_Relate` 模式，并配合包围盒条件缩小候选集：

```sql
SELECT a.id, b.id
FROM parcel a
JOIN parcel b
  ON a.geom && b.geom
 AND ST_Relate(a.geom, b.geom, 'F***1****');
```

这里职责分工很清楚：

```text
GiST 空间索引 / 包围盒
→ 排除不可能匹配的对象

GEOS 拓扑计算
→ 产生所需的内部、边界、外部相交事实

ST_Relate 模式
→ 把事实解释为“共享边线相邻”
```

### PostGIS Topology

PostGIS 另有独立的 Topology 扩展，用 Node、Edge、Face 和 TopoGeometry 管理显式拓扑。它适合：

- 共享边界；
- 面的拓扑构造；
- 拓扑编辑；
- 一致性验证；
- 基于拓扑基础元素组织高级要素。

这两个模块并存，正好体现了 GIS 拓扑的两条路线。

### 图和行业模型

道路、管网和车道网络还需要图结构与行业语义：

- 图数据库或路由引擎负责路径和可达性；
- 水务模型负责流向、阀门和水力状态；
- Lanelet2 等模型负责车道和交通规则；
- 实时系统负责把临时状态叠加到静态网络。

几何引擎不会自动生成完整业务网络，业务网络也不能替代几何质检。

## 一套分层的拓扑检查流程

面对 GIS、管网或自动驾驶地图，可以按以下顺序检查。

```text
坐标与精度
├─ CRS、单位和轴顺序正确
├─ 数据精度和容差明确
└─ 不同来源数据已经正确对齐

单个几何
├─ 环闭合
├─ 无非法自相交
├─ 洞和外环方向、包含关系合理
└─ 没有空几何和退化对象

几何关系
├─ 不应重叠的对象没有重叠
├─ 应共享的边界没有缝隙
├─ 点、线、面关联满足 DE-9IM 条件
└─ 叠加结果没有异常碎片

显式拓扑
├─ Node、Edge、Face 引用一致
├─ 左右面和边方向正确
├─ 共享边界只维护一次
└─ 拓扑元素可以重建完整要素

网络拓扑
├─ 前驱和后继一致
├─ 没有非预期悬挂
├─ 高架和地面没有错误连通
└─ 合流、分流和方向完整

业务与动态规则
├─ 转向、换道和参与者限制正确
├─ 阀门、泵站和设备状态可解释
├─ 有效时间和版本明确
└─ 静态地图能与实时状态对齐
```

这套流程也说明，不能只用一次 `IsValid` 或 `Intersects` 宣布数据“拓扑正确”。拓扑正确性永远相对于某个层次和一组业务规则。

## 拓扑发展到今天，真正发生了什么

回顾这条历史线，可以看到拓扑在 GIS 中经历了几次角色变化。

### 第一次：连接问题

```text
七桥问题
→ 抛弃长度和形状
→ 只保留节点和边
```

### 第二次：数字地图的数据结构

```text
纸质地图进入计算机
→ 保存 Node、Edge、Face
→ 维护关联、邻接和连通
```

### 第三次：空间关系的形式语言

```text
不同软件需要统一语义
→ 内部、边界、外部
→ DE-9IM 和 OGC 空间谓词
```

### 第四次：条件化的业务网络

```text
静态几何关系
+ 方向、规则、参与者、层级和时间
= 当前真正可用的空间关系
```

现代 GIS 并没有用一种新模型替代所有旧模型，而是把它们叠加起来：

```text
Geometry
描述对象在哪里、长什么样

Geometric Topology
描述相交、接触、包含和重叠

Explicit Topology
保存节点、边、面及共享关系

Network Topology
描述连接、方向和可达性

Business Semantics
描述谁在什么条件下可以使用这些连接

Temporal State
描述关系在什么时候成立
```

## 总结

拓扑最初被提出，是因为有些空间问题根本不需要计算长度和角度。欧拉解决七桥问题时，真正重要的不是桥有多长，而是陆地和桥怎样连接。

进入 GIS 后，同样的问题重新出现：坐标可以画出线条，却不能保证道路连通、地块无缝、管网可追踪，也不能统一解释“相交”“接触”和“包含”。

于是 GIS 发展出两类互补能力：

```text
节点—边—面模型
→ 显式保存共享和连接关系

DE-9IM
→ 统一计算几何对象之间的拓扑关系
```

道路、管网、河网、栅格、地籍和自动驾驶又在这些基础上增加方向、规则、层级和时间。

这一章最终想留下的认识是：

> **GIS 拓扑的本质，是把空间对象之间不能被坐标和形状细节掩盖的关系，变成可以存储、检查、推理和计算的结构。**

下一章将进入**空间计算与几何运算**，讨论缓冲区、裁剪、叠加、合并和简化怎样改变几何，以及这些操作为什么会产生碎面、无效几何和精度问题。
